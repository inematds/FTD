🏗️ As camadas de uma aplicação com IA

No módulo 2.1 você chamou um modelo direto do script. Funciona para testar, mas quebra rápido num produto: o provedor muda o preço, o modelo fica lento numa sexta-feira, mil pessoas usam ao mesmo tempo, alguém pergunta "o que eu disse ontem?". A resposta é arquitetura: separar a aplicação em camadas com responsabilidades claras, para que cada problema seja resolvido num lugar só.

A regra de ouro é a mesma do software tradicional: baixo acoplamento. A interface não sabe qual modelo está por trás; a lógica de negócio não sabe se a resposta veio do cache ou de uma GPU; trocar de provedor é mudar uma configuração. Acoplamento é o quanto uma parte depende dos detalhes de outra — quanto menor, mais barato mudar.

O que é

Arquitetura de aplicação com IA é a organização do sistema em camadas — interface, backend, orquestração, gateway de modelos e modelos — com dois serviços transversais: estado (dados e memória) e observabilidade (logs, métricas, custo).

✓ Sinais de boa arquitetura

  • ✓Trocar de modelo é mudar configuração, não código.
  • ✓Prompts vivem em arquivos versionados, com teste.
  • ✓Toda chamada ao modelo passa por um único ponto.
  • ✓Existe resposta definida para quando o modelo falha.

✗ Sinais de alerta

  • ✗Chamadas ao SDK espalhadas por dezenas de arquivos.
  • ✗Nome do modelo escrito à mão em vários lugares.
  • ✗Ninguém sabe quanto cada funcionalidade gasta.
  • ✗Se o provedor cai, a tela mostra erro 500 para o cliente.

Por que aprender

Modelos mudam rápido: o melhor de hoje é substituído em meses, e preços sobem e descem. Quem acopla o produto a um modelo específico reescreve o sistema a cada troca. Quem separa as camadas troca uma peça e segue em frente — e consegue responder a perguntas de custo, qualidade e falha com dados.

🧭 Orquestração

Orquestração é o código que decide a ordem das coisas: o que fazer antes de chamar o modelo, quantas chamadas fazer, o que checar depois. Há dois estilos. No pipeline (ou workflow), você escreve os passos em sequência fixa: limpar a entrada, buscar contexto, chamar o modelo, validar, salvar. No agente, o modelo decide o próximo passo num laço, escolhendo ferramentas até terminar.

Comece sempre pelo pipeline. Ele é previsível, barato de testar e fácil de depurar, porque cada etapa tem entrada e saída conhecidas. Use agente só quando o caminho realmente varia de caso para caso (módulo 2.5). Bibliotecas como LangGraph ajudam a desenhar os dois estilos como grafos de etapas, mas um pipeline simples cabe em funções Python comuns — não é preciso framework para começar.

O que é

Orquestração é a camada que encadeia as etapas em volta do modelo — pré-processamento, chamada, validação, pós-processamento — com portões de qualidade entre elas. Pode ser um pipeline fixo ou um agente que escolhe o próximo passo.

Pré-processar. Normalize o texto, corte o que é grande demais, troque dados pessoais por marcadores (LGPD) e detecte o idioma.

Montar o contexto. Junte o system, a memória da sessão e, se houver, os trechos de documentos buscados (RAG, módulo 2.3).

Chamar pelo gateway. Nunca direto no SDK: o gateway escolhe o modelo, aplica cache e fallback.

Validar. Schema, tamanho, palavras proibidas, regras do negócio ("desconto nunca acima do permitido").

Pós-processar e registrar. Formatar para a tela, restaurar os marcadores, gravar tokens, latência e resultado.

Por que aprender

A maior parte da qualidade de um produto com IA vem do que acontece antes e depois da chamada, não do modelo. Um pipeline com portões transforma "às vezes o modelo responde errado" em "quando o modelo erra, o sistema percebe e reage" — que é o que um cliente consegue aceitar.

Pipeline

LangGraph

🔀 Gateway de modelos

O gateway de modelos é uma função (ou um serviço) pela qual passa toda chamada a modelo. O resto do sistema pede por tarefa — "classificar", "resumir", "responder com qualidade" — e o gateway decide qual modelo usar, em que ordem tentar e o que devolver se tudo falhar. É o padrão adapter do software clássico aplicado a modelos: uma interface única na frente de vários provedores.

A peça mais valiosa do gateway é o fallback: uma lista ordenada de alternativas. Se o primeiro modelo der erro ou estourar o tempo, tenta o segundo; se todos falharem, devolve uma resposta padrão honesta em vez de uma tela de erro. Bibliotecas como LiteLLM já fazem isso para dezenas de provedores; o exemplo abaixo mostra o mecanismo em poucas linhas, para você entender o que elas fazem.

O que é

Um ponto único de acesso a modelos que roteia cada tarefa para o modelo certo, tenta alternativas em ordem quando um falha, mede tempo e tokens e esconde do resto do sistema qual provedor está sendo usado.

Experimente: um gateway com rotas por tarefa e fallback.

# gateway.py  (pip install openai · ollama pull llama3.2 · ollama pull qwen2.5)
import os, time
from openai import OpenAI

PROVEDORES = {
    "local": OpenAI(base_url="http://localhost:11434/v1", api_key="ollama", timeout=60, max_retries=0),
    # API paga: mesma interface, outra URL e chave (lida do ambiente, nunca escrita aqui)
    # "nuvem": OpenAI(base_url="https://<provedor>/v1", api_key=os.environ["LLM_API_KEY"]),
}

# Cada tarefa tem uma lista ordenada de (provedor, modelo). A primeira que responder vence.
ROTAS = {
    "classificar": [("local", "llama3.2"), ("local", "qwen2.5")],
    "responder":   [("local", "qwen2.5"), ("local", "llama3.2")],
}

RESPOSTA_PADRAO = "Não consegui responder agora. Sua mensagem foi registrada e retornamos em breve."

def completar(tarefa, messages, **kw):
    for provedor, modelo in ROTAS[tarefa]:
        inicio = time.perf_counter()
        try:
            r = PROVEDORES[provedor].chat.completions.create(model=modelo, messages=messages, **kw)
            ms = (time.perf_counter() - inicio) * 1000
            print(f"[ok] {tarefa} via {provedor}/{modelo} em {ms:.0f} ms, {r.usage.completion_tokens} tokens")
            return r.choices[0].message.content
        except Exception as e:
            print(f"[falhou] {provedor}/{modelo}: {type(e).__name__}; tentando o próximo")
    return RESPOSTA_PADRAO

if __name__ == "__main__":
    msg = [
        {"role": "system", "content": "Você classifica chamados de clientes. Categorias: "
            "VENDAS = quer comprar ou saber preço; SUPORTE = problema técnico ou dúvida de uso; "
            "FINANCEIRO = boleto, cobrança, pagamento ou reembolso. Responda só com a categoria."},
        {"role": "user", "content": "Chamado: meu boleto veio duplicado"},
    ]
    print(completar("classificar", msg, temperature=0, max_tokens=10))

Como verificar: a saída mostra uma linha [ok] classificar via local/llama3.2 … e a categoria (esperado: FINANCEIRO). Agora troque "llama3.2" da rota classificar por "nao-existe": deve aparecer [falhou] local/nao-existe: NotFoundError e a resposta vir do qwen2.5. Desligue o Ollama: as duas falham e sai a resposta padrão, sem traceback.

Estratégia de rotaComo decideBom para
Por tarefaCada tipo de pedido tem sua lista de modelos.Começar; é o mais simples de entender.
Em cascataTenta o modelo barato; se a validação reprovar, sobe para o melhor.Volume alto com casos difíceis raros.
Por sensibilidadeDados pessoais ou sigilosos vão só para o modelo local.LGPD e contratos de confidencialidade.

Por que aprender

Com um gateway, testar um modelo novo é mudar uma linha da tabela de rotas, comparar e voltar se não gostar. Quedas de provedor viram uma linha de log em vez de um incidente. E a pergunta "quanto custa cada funcionalidade?" passa a ter resposta, porque toda chamada passa pelo mesmo lugar.

🧠 Estado e memória

Como a API não tem estado, a memória é sua: você decide o que entra em cada chamada. A memória de curto prazo são as mensagens recentes da sessão. A de longo prazo são fatos que valem entre sessões — o nome do cliente, o plano contratado, as preferências — guardados num banco e injetados quando relevantes. O histórico completo pode ficar no banco para auditoria; o que vai para o modelo é uma seleção.

A técnica mais usada para conversas longas é a janela deslizante com resumo: as últimas N mensagens vão inteiras; as antigas são condensadas num resumo curto, atualizado de tempos em tempos pelo próprio modelo. Assim o tamanho do pedido fica estável, o custo também, e o essencial não se perde. Para armazenar, SQLite basta num protótipo; em produção, Postgres ou Redis.

O que é

Gerenciar estado é decidir onde a conversa é guardada (banco), o que dela volta para o modelo (janela recente + resumo + fatos de longo prazo) e por quanto tempo cada coisa é mantida.

Objetivo: um chat com memória persistente em SQLite, janela deslizante e resumo.

# memoria.py  (pip install openai · ollama pull llama3.2)
import sqlite3, sys
from openai import OpenAI

client = OpenAI(base_url="http://localhost:11434/v1", api_key="ollama")
MODELO, JANELA, RESUMIR_A_CADA = "llama3.2", 6, 6

db = sqlite3.connect("conversas.db")
db.execute("CREATE TABLE IF NOT EXISTS msgs (id INTEGER PRIMARY KEY, sessao TEXT, papel TEXT, texto TEXT)")
db.execute("CREATE TABLE IF NOT EXISTS resumos (sessao TEXT PRIMARY KEY, texto TEXT)")

def chat(messages, max_tokens=300):
    r = client.chat.completions.create(model=MODELO, messages=messages, max_tokens=max_tokens)
    return r.choices[0].message.content

def salvar(sessao, papel, texto):
    db.execute("INSERT INTO msgs (sessao, papel, texto) VALUES (?, ?, ?)", (sessao, papel, texto))
    db.commit()

def recentes(sessao, n):
    linhas = db.execute("SELECT papel, texto FROM msgs WHERE sessao = ? ORDER BY id DESC LIMIT ?", (sessao, n)).fetchall()
    return [{"role": p, "content": t} for p, t in reversed(linhas)]

def atualizar_resumo(sessao):
    tudo = recentes(sessao, 1000)
    texto = "\n".join(f"{m['role']}: {m['content']}" for m in tudo)
    resumo = chat([{"role": "user", "content": "Resuma em até 5 linhas os fatos importantes desta conversa "
                    "(nomes, pedidos, decisões):\n" + texto}], max_tokens=200)
    db.execute("INSERT OR REPLACE INTO resumos (sessao, texto) VALUES (?, ?)", (sessao, resumo))
    db.commit()

def conversar(sessao, pergunta):
    msgs = [{"role": "system", "content": "Você é um atendente de suporte. Responda curto, em português."}]
    linha = db.execute("SELECT texto FROM resumos WHERE sessao = ?", (sessao,)).fetchone()
    if linha:
        msgs.append({"role": "system", "content": "Resumo da conversa até aqui:\n" + linha[0]})
    msgs += recentes(sessao, JANELA) + [{"role": "user", "content": pergunta}]
    resposta = chat(msgs)
    salvar(sessao, "user", pergunta)
    salvar(sessao, "assistant", resposta)
    total = db.execute("SELECT COUNT(*) FROM msgs WHERE sessao = ?", (sessao,)).fetchone()[0]
    if total % RESUMIR_A_CADA == 0:
        atualizar_resumo(sessao)
    return resposta

if __name__ == "__main__":
    sessao = sys.argv[1] if len(sys.argv) > 1 else "demo"
    while True:
        pergunta = input("você: ").strip()
        if pergunta in ("", "sair"):
            break
        print("ia:", conversar(sessao, pergunta))

Como verificar: rode python3 memoria.py ana, diga "meu nome é Ana e meu pedido é o 4521", converse mais umas quatro mensagens e digite sair. Rode de novo com ana e pergunte "qual é o número do meu pedido?" — a resposta vem do banco, não da memória do programa. Confira o resumo com sqlite3 conversas.db "select texto from resumos". Com python3 memoria.py bia, a sessão começa vazia.

💡 Dica

Memória é dado pessoal. Defina por quanto tempo cada sessão fica guardada, permita apagar a pedido do titular (LGPD) e não guarde no resumo o que não precisa — número de cartão, senha e documento nunca deveriam chegar lá.

Por que aprender

Um assistente que esquece o que o cliente disse três mensagens atrás irrita; um que reenvia a conversa inteira a cada pergunta fica caro e lento. Gerenciar a memória de propósito é o que faz um chatbot parecer atento sem que a conta cresça junto com a conversa.

⚡ Cache

Cache é guardar o resultado de uma operação cara para reaproveitar quando o mesmo pedido voltar. Em aplicações com IA há vários níveis: o cache exato (mesmo modelo, mesmas mensagens, mesmos parâmetros → mesma resposta), o cache semântico (perguntas diferentes com o mesmo sentido, comparadas por embeddings — módulo 2.3), o cache de embeddings de documentos e o cache de prompt que os próprios provedores oferecem.

Cache tem um preço: a resposta pode ficar velha. Por isso todo cache precisa de uma regra de validade — o TTL (time to live, tempo de vida) — e de uma forma de ser invalidado quando a fonte muda. E só faz sentido para respostas que deveriam ser iguais: use com temperature=0 e nunca para conteúdo personalizado de um usuário servido a outro.

O que é

Cache é uma memória de respostas já calculadas, consultada antes de chamar o modelo. A chave identifica o pedido (exata ou por semelhança), o TTL define quanto tempo a resposta vale.

TipoChaveCuidado
ExatoHash de modelo + mensagens + parâmetros.Só acerta pedidos idênticos.
SemânticoEmbedding da pergunta, com limiar de semelhança.Limiar frouxo devolve resposta da pergunta errada.
De embeddingsHash do trecho de documento.Recalcular tudo se trocar o modelo de embedding.
De prompt (provedor)Começo idêntico do pedido, feito pelo provedor.Coloque o que é fixo no início e o variável no fim.

Experimente: cache exato em SQLite com TTL, na frente do modelo.

# cache.py  (pip install openai · ollama pull llama3.2)
import hashlib, json, sqlite3, time
from openai import OpenAI

client = OpenAI(base_url="http://localhost:11434/v1", api_key="ollama")
TTL = 24 * 3600  # um dia

db = sqlite3.connect("cache.db")
db.execute("CREATE TABLE IF NOT EXISTS cache (chave TEXT PRIMARY KEY, resposta TEXT, criado REAL)")

def chave(modelo, messages, params):
    bruto = json.dumps({"m": modelo, "msgs": messages, "p": params}, sort_keys=True, ensure_ascii=False)
    return hashlib.sha256(bruto.encode()).hexdigest()

def completar(messages, modelo="llama3.2", **params):
    params.setdefault("temperature", 0)  # cache só faz sentido com saída estável
    k = chave(modelo, messages, params)
    linha = db.execute("SELECT resposta, criado FROM cache WHERE chave = ?", (k,)).fetchone()
    if linha and time.time() - linha[1] < TTL:
        return linha[0], "HIT"
    r = client.chat.completions.create(model=modelo, messages=messages, **params)
    texto = r.choices[0].message.content
    db.execute("INSERT OR REPLACE INTO cache VALUES (?, ?, ?)", (k, texto, time.time()))
    db.commit()
    return texto, "MISS"

if __name__ == "__main__":
    pergunta = [{"role": "user", "content": "Em uma frase: o que é TTL num cache?"}]
    for _ in range(2):
        t = time.perf_counter()
        texto, status = completar(pergunta, max_tokens=80)
        print(f"{status} em {(time.perf_counter() - t) * 1000:.0f} ms: {texto}")

Como verificar: a primeira linha sai como MISS, com o tempo de geração do modelo; a segunda como HIT, em poucos milissegundos e com o mesmo texto. Rode o script de novo: agora as duas linhas são HIT, porque o cache está no arquivo cache.db. Mude uma vírgula da pergunta e volta a dar MISS — é o limite do cache exato.

Por que aprender

Muitos sistemas recebem as mesmas perguntas o tempo todo: horário de funcionamento, política de troca, status de serviço. Responder do cache é mais rápido para o usuário e não gasta token. Saber onde o cache ajuda — e onde ele serve resposta velha ou de outra pessoa — é parte do desenho, não um ajuste final.

📬 Filas e trabalho assíncrono

Resumir um contrato de cem páginas, transcrever uma reunião ou processar mil e-mails não cabe numa requisição web: o navegador desiste antes. A solução é a fila: a API recebe o pedido, grava um "trabalho" numa fila e responde na hora com um identificador. Processos separados, os workers, pegam os trabalhos um a um, chamam o modelo e salvam o resultado. O usuário consulta o status ou é avisado quando termina.

Ferramentas consagradas para isso: Celery e RQ no Python, BullMQ no Node, quase sempre com Redis por trás; em automações, n8n e Make fazem papel parecido. Dois conceitos evitam dor de cabeça. Idempotência: rodar o mesmo trabalho duas vezes não pode gerar efeito duplicado (dois e-mails, duas cobranças). Fila de mensagens mortas (DLQ, dead letter queue): trabalhos que falharam várias vezes vão para um canto separado, para alguém olhar, em vez de travar a fila.

O que é

Processamento assíncrono é separar o "receber o pedido" do "fazer o trabalho": uma fila guarda os trabalhos e workers independentes os executam no ritmo que o modelo e o orçamento aguentam.

✓ Vá para a fila quando

  • ✓A tarefa leva mais que alguns segundos.
  • ✓Chegam muitos pedidos de uma vez (importação, campanha).
  • ✓Você precisa respeitar limite de taxa ou de GPU.
  • ✓O resultado pode chegar por e-mail, aviso ou webhook.

✗ Fila não resolve

  • ✗Chat em que a pessoa espera a resposta (use streaming).
  • ✗Trabalhos sem idempotência: reprocessar duplica efeitos.
  • ✗Fila sem monitoramento: cresce em silêncio até alguém reclamar.
  • ✗Modelo lento demais para o volume: aí é preciso outro modelo.

Por que aprender

É a fila que permite processar documentos em lote, rodar o modelo local de madrugada e absorver picos sem derrubar o sistema. Também é o que permite usar as APIs em lote dos provedores, mais baratas, porque o resultado não precisa sair na hora.

🔭 Observabilidade e degradação elegante

Observabilidade é conseguir responder, olhando os registros, a qualquer pergunta sobre o sistema: por que essa resposta saiu errada, qual funcionalidade gastou mais tokens ontem, quando a latência piorou. Em IA, os sinais essenciais por chamada são: modelo usado, tokens de entrada e saída, latência, resultado da validação, erro (se houve) e um identificador que liga todas as etapas de um mesmo pedido — o trace. O padrão aberto OpenTelemetry e ferramentas como Langfuse organizam isso.

Degradação elegante é o sistema perder qualidade aos poucos em vez de quebrar de uma vez. Um circuit breaker (disjuntor) ajuda: depois de várias falhas seguidas de um provedor, o gateway para de chamá-lo por um tempo e vai direto ao plano B, em vez de fazer cada usuário esperar um tempo esgotado. Defina por escrito a escada de degraus antes de precisar dela.

O que é

Observabilidade é registrar, por chamada e por pedido, o que o sistema fez e quanto custou. Degradação elegante é ter degraus de resposta cada vez mais simples — e honestos — para quando as peças falham.

DegrauSituaçãoO que o usuário vê
1 · NormalModelo principal respondendo.Resposta completa.
2 · AlternativoPrincipal falhou; fallback para outro modelo.Resposta, talvez mais simples.
3 · Cache / FAQNenhum modelo disponível.Resposta pronta para perguntas frequentes.
4 · FilaSem resposta possível agora."Registramos seu pedido; respondemos em breve."
5 · HumanoTema sensível ou falha prolongada.Encaminhamento para uma pessoa.

💡 Dica

Comece simples: no gateway do tópico 3, grave uma linha JSON por chamada num arquivo ({"trace": …, "tarefa": …, "modelo": …, "ms": …, "tokens_in": …, "tokens_out": …, "ok": …}). Só com isso você já monta um painel de custo e latência. Não grave o texto completo de conversas com dados pessoais; guarde o necessário para depurar, por tempo definido.

🧩 Termos novos

Trace: o rastro de um pedido por todas as etapas, ligado por um mesmo identificador. Span: cada etapa dentro do trace (buscar contexto, chamar modelo, validar). Eval: um conjunto fixo de perguntas com respostas esperadas, rodado a cada mudança de prompt ou modelo para ver se a qualidade caiu.

Por que aprender

Modelos erram de um jeito silencioso: a resposta sai bem escrita e errada, sem exceção nenhuma no log. Sem observabilidade você só descobre pelo cliente. E sem degraus de degradação, a queda de um provedor externo vira a queda do seu produto inteiro.
