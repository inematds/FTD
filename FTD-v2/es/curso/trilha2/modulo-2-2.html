🏗️ Las capas de una aplicación con IA

En el módulo 2.1 llamaste a un modelo directamente desde el script. Funciona para probar, pero falla rápidamente en un producto: el proveedor cambia el precio, el modelo se vuelve lento un viernes, mil personas lo usan al mismo tiempo, alguien pregunta «¿qué dije ayer?». La respuesta es arquitectura: separar la aplicación en capas con responsabilidades claras, para que cada problema se resuelva en un solo lugar.

La regla de oro es la misma que en el software tradicional: bajo acoplamiento. La interfaz no sabe qué modelo hay detrás; la lógica de negocio no sabe si la respuesta vino de la caché o de una GPU; cambiar de proveedor consiste en modificar una configuración. El acoplamiento es cuánto depende una parte de los detalles de otra: cuanto menor sea, menos cuesta cambiar.

Qué es

La arquitectura de una aplicación con IA es la organización del sistema en capas —interfaz, backend, orquestación, gateway de modelos y modelos— con dos servicios transversales: estado (datos y memoria) y observabilidad (registros, métricas, costo).

✓ Señales de una buena arquitectura

  • ✓Cambiar de modelo es modificar la configuración, no el código.
  • ✓Los prompts están en archivos versionados y cuentan con pruebas.
  • ✓Todas las llamadas al modelo pasan por un único punto.
  • ✓Hay una respuesta definida para cuando falla el modelo.

✗ Señales de alerta

  • ✗Llamadas al SDK repartidas en decenas de archivos.
  • ✗El nombre del modelo escrito a mano en varios lugares.
  • ✗Nadie sabe cuánto cuesta cada funcionalidad.
  • ✗Si el proveedor se cae, el cliente ve un error 500 en la pantalla.

Por qué aprender

Los modelos cambian rápido: el mejor de hoy queda reemplazado en unos meses, y los precios suben y bajan. Quien acopla el producto a un modelo específico reescribe el sistema cada vez que cambia. Quien separa las capas cambia una pieza y sigue adelante, y puede responder preguntas sobre costo, calidad y fallas con datos.

🧭 Orquestación

Orquestación es el código que decide el orden de las cosas: qué hacer antes de llamar al modelo, cuántas llamadas hacer y qué revisar después. Hay dos estilos. En el pipeline (o workflow), escribes los pasos en una secuencia fija: limpiar la entrada, buscar contexto, llamar al modelo, validar y guardar. En el agente, el modelo decide el siguiente paso en un ciclo y elige herramientas hasta terminar.

Empieza siempre por el pipeline. Es predecible, barato de probar y fácil de depurar, porque cada etapa tiene entradas y salidas conocidas. Usa un agente solo cuando el camino realmente varía según el caso (módulo 2.5). Bibliotecas como LangGraph ayudan a diseñar ambos estilos como grafos de etapas, pero un pipeline sencillo cabe en funciones comunes de Python: no necesitas un framework para empezar.

Qué es

La orquestación es la capa que encadena las etapas alrededor del modelo —preprocesamiento, llamada, validación y posprocesamiento— con controles de calidad entre ellas. Puede ser un pipeline fijo o un agente que elige el siguiente paso.

Preprocesar. Normaliza el texto, recorta lo que sea demasiado extenso, reemplaza los datos personales por marcadores (LGPD, ley brasileña de protección de datos) y detecta el idioma.

Armar el contexto. Combina el system, la memoria de la sesión y, si los hay, los fragmentos de documentos encontrados (RAG, módulo 2.3).

Llamar a través del gateway. Nunca directamente desde el SDK: el gateway elige el modelo, aplica caché y fallback.

Validar. Esquema, longitud, palabras prohibidas, reglas del negocio («el descuento nunca debe superar el límite permitido»).

Posprocesar y registrar. Dar formato para la pantalla, restaurar los marcadores, registrar tokens, latencia y resultado.

Por qué aprender

La mayor parte de la calidad de un producto con IA proviene de lo que ocurre antes y después de la llamada, no del modelo. Un pipeline con controles transforma «a veces el modelo responde mal» en «cuando el modelo se equivoca, el sistema lo detecta y reacciona»: eso es algo que un cliente puede aceptar.

Control de calidad

🔀 Gateway de modelos

O gateway de modelos es una función (o un servicio) por la que pasa cada llamada a un modelo. El resto del sistema solicita una tarea —«clasificar», «resumir», «responder con calidad»— y el gateway decide qué modelo usar, en qué orden probarlos y qué devolver si todo falla. Es el patrón adapter del software clásico aplicado a los modelos: una interfaz única frente a varios proveedores.

La pieza más valiosa del gateway es el fallback: una lista ordenada de alternativas. Si el primer modelo da error o se agota el tiempo de espera, prueba con el segundo; si todos fallan, devuelve una respuesta estándar honesta en lugar de una pantalla de error. Bibliotecas como LiteLLM ya hacen esto para decenas de proveedores; el ejemplo de abajo muestra el mecanismo en unas pocas líneas, para que entiendas qué hacen.

Qué es

Un único punto de acceso a los modelos que dirige cada tarea al modelo adecuado, prueba alternativas en orden cuando uno falla, mide el tiempo y los tokens, y oculta al resto del sistema qué proveedor se está usando.

Prueba: un gateway con rutas por tarea y fallback.

# gateway.py  (pip install openai · ollama pull llama3.2 · ollama pull qwen2.5)
import os, time
from openai import OpenAI

PROVEDORES = {
    "local": OpenAI(base_url="http://localhost:11434/v1", api_key="ollama", timeout=60, max_retries=0),
    # API de pago: misma interfaz, otra URL y clave (leída del entorno, nunca escrita aquí)
    # "nuvem": OpenAI(base_url="https://<proveedor>/v1", api_key=os.environ["LLM_API_KEY"]),
}

# Cada tarea tiene una lista ordenada de (proveedor, modelo). Gana el primero que responda.
ROTAS = {
    "classificar": [("local", "llama3.2"), ("local", "qwen2.5")],
    "responder":   [("local", "qwen2.5"), ("local", "llama3.2")],
}

RESPOSTA_PADRAO = "No pude responder en este momento. Tu mensaje quedó registrado y te responderemos pronto."

def completar(tarefa, messages, **kw):
    for provedor, modelo in ROTAS[tarefa]:
        inicio = time.perf_counter()
        try:
            r = PROVEDORES[provedor].chat.completions.create(model=modelo, messages=messages, **kw)
            ms = (time.perf_counter() - inicio) * 1000
            print(f"[ok] {tarefa} via {provedor}/{modelo} en {ms:.0f} ms, {r.usage.completion_tokens} tokens")
            return r.choices[0].message.content
        except Exception as e:
            print(f"[falló] {provedor}/{modelo}: {type(e).__name__}; intentando el siguiente")
    return RESPOSTA_PADRAO

if __name__ == "__main__":
    msg = [
        {"role": "system", "content": "Clasificas solicitudes de clientes. Categorías: "
            "VENTAS = quiere comprar o saber el precio; SOPORTE = problema técnico o duda sobre el uso; "
            "FINANZAS = factura, cobro, pago o reembolso. Responde solo con la categoría."},
        {"role": "user", "content": "Solicitud: mi factura llegó duplicada"},
    ]
    print(completar("classificar", msg, temperature=0, max_tokens=10))

Cómo verificar: la salida muestra una línea [ok] clasificar via local/llama3.2 … y la categoría (esperada: FINANZAS). Ahora cambia "llama3.2" de la ruta classificar por "nao-existe": debe aparecer [falló] local/nao-existe: NotFoundError y la respuesta debe venir de qwen2.5. Apaga Ollama: ambos fallan y aparece la respuesta predeterminada, sin traceback.

Estrategia de rutaCómo decideIdeal para
Por tareaCada tipo de solicitud tiene su propia lista de modelos.Para empezar; es lo más fácil de entender.
En cascadaPrueba el modelo barato; si la validación lo rechaza, pasa al mejor.Mucho volumen con pocos casos difíciles.
Por sensibilidadLos datos personales o confidenciales solo se envían al modelo local.LGPD y contratos de confidencialidad.

Por qué aprender

Con un gateway, probar un modelo nuevo consiste en cambiar una línea de la tabla de rutas, comparar y volver atrás si no te gusta. Las caídas del proveedor se convierten en una línea de registro en lugar de un incidente. Y la pregunta "¿cuánto cuesta cada funcionalidad?" tiene respuesta, porque todas las llamadas pasan por el mismo lugar.

🧠 Estado y memoria

Como la API no tiene estado, la memoria es tuya: decides qué se incluye en cada llamada. La memoria de corto plazo son los mensajes recientes de la sesión. La de largo plazo son datos que siguen siendo válidos entre sesiones —el nombre del cliente, el plan contratado, sus preferencias—, guardados en una base de datos e incluidos cuando son relevantes. El historial completo puede quedar en la base de datos para auditoría; al modelo se le envía una selección.

La técnica más usada para conversaciones largas es la ventana deslizante con resumen: las últimas N conversaciones se envían completas; las anteriores se condensan en un resumen breve, que el propio modelo actualiza cada cierto tiempo. Así, el tamaño de la solicitud se mantiene estable, al igual que el costo, y no se pierde lo esencial. Para almacenar los datos, SQLite basta en un prototipo; en producción, usa Postgres o Redis.

Qué es

Gestionar el estado consiste en decidir dónde se guarda la conversación (base de datos), qué partes vuelven al modelo (ventana reciente + resumen + datos de largo plazo) y durante cuánto tiempo se conserva cada elemento.

Objetivo: un chat con memoria persistente en SQLite, ventana deslizante y resumen.

# memoria.py  (pip install openai · ollama pull llama3.2)
import sqlite3, sys
from openai import OpenAI

client = OpenAI(base_url="http://localhost:11434/v1", api_key="ollama")
MODELO, JANELA, RESUMIR_A_CADA = "llama3.2", 6, 6

db = sqlite3.connect("conversas.db")
db.execute("CREATE TABLE IF NOT EXISTS msgs (id INTEGER PRIMARY KEY, sessao TEXT, papel TEXT, texto TEXT)")
db.execute("CREATE TABLE IF NOT EXISTS resumos (sessao TEXT PRIMARY KEY, texto TEXT)")

def chat(messages, max_tokens=300):
    r = client.chat.completions.create(model=MODELO, messages=messages, max_tokens=max_tokens)
    return r.choices[0].message.content

def salvar(sessao, papel, texto):
    db.execute("INSERT INTO msgs (sessao, papel, texto) VALUES (?, ?, ?,)", (sessao, papel, texto))
    db.commit()

def recentes(sessao, n):
    linhas = db.execute("SELECT papel, texto FROM msgs WHERE sessao = ? ORDER BY id DESC LIMIT ?", (sessao, n)).fetchall()
    return [{"role": p, "content": t} for p, t in reversed(linhas)]

def atualizar_resumo(sessao):
    tudo = recentes(sessao, 1000)
    texto = "\n".join(f"{m['role']}: {m['content']}" for m in tudo)
    resumo = chat([{"role": "user", "content": "Resume en hasta 5 líneas los hechos importantes de esta conversación "
                    "(nombres, pedidos, decisiones):\n" + texto}], max_tokens=200)
    db.execute("INSERT OR REPLACE INTO resumos (sessao, texto) VALUES (?, ?)", (sessao, resumo))
    db.commit()

def conversar(sessao, pergunta):
    msgs = [{"role": "system", "content": "Eres un agente de soporte. Responde brevemente, en portugués."}]
    linha = db.execute("SELECT texto FROM resumos WHERE sessao = ?", (sessao,)).fetchone()
    if linha:
        msgs.append({"role": "system", "content": "Resumen de la conversación hasta aquí:\n" + linha[0]})
    msgs += recentes(sessao, JANELA) + [{"role": "user", "content": pergunta}]
    resposta = chat(msgs)
    salvar(sessao, "user", pergunta)
    salvar(sessao, "assistant", resposta)
    total = db.execute("SELECT COUNT(*) FROM msgs WHERE sessao = ?", (sessao,)).fetchone()[0]
    if total % RESUMIR_A_CADA == 0:
        atualizar_resumo(sessao)
    return resposta

if __name__ == "__main__":
    sessao = sys.argv[1] if len(sys.argv) > 1 else "demo"
    while True:
        pergunta = input("tú: ").strip()
        if pergunta in ("", "sair"):
            break
        print("ia:", conversar(sessao, pergunta))

Cómo verificar: ejecuta python3 memoria.py ana, di «me llamo Ana y mi número de pedido es el 4521», conversa unas cuatro veces más y escribe salir. Vuelve a ejecutar con ana y pregunta «¿cuál es el número de mi pedido?» — la respuesta viene de la base de datos, no de la memoria del programa. Revisa el resumen con sqlite3 conversas.db "select texto from resumos". Con python3 memoria.py bia, la sesión empieza vacía.

💡 Consejo

La memoria contiene datos personales. Define cuánto tiempo se conserva cada sesión, permite que la persona titular solicite su eliminación (LGPD) y no guardes en el resumen lo que no hace falta: nunca deberían llegar ahí números de tarjeta, contraseñas ni documentos.

Por qué aprender

Un asistente que olvida lo que el cliente dijo hace tres mensajes irrita; uno que reenvía toda la conversación con cada pregunta resulta caro y lento. Gestionar la memoria de forma deliberada es lo que hace que un chatbot parezca atento sin que la cuenta crezca junto con la conversación.

⚡ Caché

Caché consiste en guardar el resultado de una operación costosa para reutilizarlo cuando vuelva a aparecer la misma solicitud. En las aplicaciones con IA hay varios niveles: la caché exacta (mismo modelo, mismos mensajes, mismos parámetros → misma respuesta), la caché semántica (preguntas distintas con el mismo sentido, comparadas mediante embeddings — módulo 2.3), la caché de embeddings de documentos y la caché de prompts que ofrecen los propios proveedores.

La caché tiene un costo: la respuesta puede quedar desactualizada. Por eso, toda caché necesita una regla de validez: el TTL (tiempo de vida) — y una forma de invalidarla cuando cambia la fuente. Además, solo tiene sentido para respuestas que deberían ser iguales: úsala con temperature=0 y nunca para mostrarle a una persona el contenido personalizado de otra.

Qué es

La caché es una memoria de respuestas ya calculadas que se consulta antes de llamar al modelo. La clave identifica la solicitud (de forma exacta o por similitud); el TTL define cuánto tiempo es válida la respuesta.

TipoClaveCuidado
ExactaHash del modelo + mensajes + parámetros.Solo coincide con solicitudes idénticas.
SemánticaEmbedding de la pregunta, con un umbral de similitud.Un umbral demasiado bajo devuelve una respuesta a la pregunta equivocada.
De embeddingsHash del fragmento del documento.Recalcular todo si cambias el modelo de embeddings.
De prompt (proveedor)Inicio idéntico de la solicitud, almacenado por el proveedor.Pon lo que es fijo al inicio y lo variable al final.

Prueba: caché exacta en SQLite con TTL, delante del modelo.

# cache.py  (pip install openai · ollama pull llama3.2)
import hashlib, json, sqlite3, time
from openai import OpenAI

client = OpenAI(base_url="http://localhost:11434/v1", api_key="ollama")
TTL = 24 * 3600  # un día

db = sqlite3.connect("cache.db")
db.execute("CREATE TABLE IF NOT EXISTS cache (chave TEXT PRIMARY KEY, resposta TEXT, criado REAL)")

def chave(modelo, messages, params):
    bruto = json.dumps({"m": modelo, "msgs": messages, "p": params}, sort_keys=True, ensure_ascii=False)
    return hashlib.sha256(bruto.encode()).hexdigest()

def completar(messages, modelo="llama3.2", **params):
    params.setdefault("temperature", 0)  # el caché solo tiene sentido con una salida estable
    k = chave(modelo, messages, params)
    linha = db.execute("SELECT resposta, criado FROM cache WHERE chave = ?", (k,)).fetchone()
    if linha and time.time() - linha[1] < TTL:
        return linha[0], "HIT"
    r = client.chat.completions.create(model=modelo, messages=messages, **params)
    texto = r.choices[0].message.content
    db.execute("INSERT OR REPLACE INTO cache VALUES (?, ?, ?)", (k, texto, time.time()))
    db.commit()
    return texto, "MISS"

if __name__ == "__main__":
    pergunta = [{"role": "user", "content": "En una frase: ¿qué es TTL en un caché?"}]
    for _ in range(2):
        t = time.perf_counter()
        texto, status = completar(pergunta, max_tokens=80)
        print(f"{status} en {(time.perf_counter() - t) * 1000:.0f} ms: {texto}")

Cómo verificar: la primera línea aparece como MISS, con el tiempo de generación del modelo; la segunda, como HIT, en unos pocos milisegundos y con el mismo texto. Ejecuta el script de nuevo: ahora las dos líneas aparecen como HIT, porque el caché está en el archivo cache.db. Cambia una coma de la pregunta y vuelve a aparecer MISS — ese es el límite del caché exacto.

Por qué aprender

Muchos sistemas reciben las mismas preguntas todo el tiempo: horario de atención, política de cambios, estado del servicio. Responder desde el caché es más rápido para el usuario y no consume tokens. Saber dónde ayuda el caché —y dónde devuelve una respuesta vieja o de otra persona— forma parte del diseño, no es un ajuste final.

📬 Colas y trabajo asíncrono

Resumir un contrato de cien páginas, transcribir una reunión o procesar mil correos no cabe en una solicitud web: el navegador se rinde antes. La solución es la cola: la API recibe la solicitud, guarda un «trabajo» en una cola y responde de inmediato con un identificador. Procesos separados, los workers, toman los trabajos uno por uno, llaman al modelo y guardan el resultado. El usuario consulta el estado o recibe un aviso cuando termina.

Herramientas consolidadas para esto: Celery y RQ en Python, BullMQ en Node, casi siempre con Redis detrás; en automatizaciones, n8n y Make cumplen una función parecida. Dos conceptos evitan dolores de cabeza. Idempotencia: ejecutar el mismo trabajo dos veces no puede generar efectos duplicados (dos correos, dos cobros). Cola de mensajes fallidos (DLQ, dead letter queue): los trabajos que fallaron varias veces van a un lugar separado para que alguien los revise, en vez de bloquear la cola.

Qué es

El procesamiento asíncrono consiste en separar «recibir la solicitud» de «hacer el trabajo»: una cola guarda los trabajos y workers independientes los ejecutan al ritmo que soportan el modelo y el presupuesto.

✓ Usa una cola cuando

  • ✓La tarea tarda más de unos segundos.
  • ✓Llegan muchas solicitudes a la vez (importación, campaña).
  • ✓Necesitas respetar un límite de tasa o de GPU.
  • ✓El resultado puede llegar por correo, aviso o webhook.

✗ La cola no resuelve

  • ✗Un chat en el que la persona espera la respuesta (usa streaming).
  • ✗Trabajos sin idempotencia: reprocesarlos duplica los efectos.
  • ✗Una cola sin monitoreo: crece en silencio hasta que alguien se queja.
  • ✗Un modelo demasiado lento para el volumen: en ese caso se necesita otro modelo.

Por qué aprender

La cola permite procesar documentos por lotes, ejecutar el modelo local durante la madrugada y absorber picos sin derribar el sistema. También permite usar las APIs por lotes de los proveedores, que son más baratas, porque el resultado no tiene que estar listo de inmediato.

🔭 Observabilidad y degradación elegante

Observabilidad es poder responder, al revisar los registros, cualquier pregunta sobre el sistema: por qué esta respuesta salió mal, qué funcionalidad consumió más tokens ayer, cuándo empeoró la latencia. En IA, las señales esenciales de cada llamada son: modelo usado, tokens de entrada y salida, latencia, resultado de la validación, error (si lo hubo) y un identificador que conecta todas las etapas de una misma solicitud: el trace. El estándar abierto OpenTelemetry y herramientas como Langfuse organizan esta información.

La degradación elegante consiste en que el sistema pierda calidad poco a poco en vez de fallar de golpe. Un circuit breaker (disyuntor) ayuda: después de varios fallos seguidos de un proveedor, el gateway deja de llamarlo por un tiempo y pasa directamente al plan B, en lugar de hacer que cada usuario espere hasta que se agote el tiempo de espera. Define por escrito los niveles de respuesta antes de necesitarlos.

Qué es

La observabilidad consiste en registrar, por llamada y por solicitud, qué hizo el sistema y cuánto costó. La degradación elegante consiste en tener niveles de respuesta cada vez más simples —y honestos— para cuando fallen las piezas.

NivelSituaciónLo que ve el usuario
1 · NormalEl modelo principal responde.Respuesta completa.
2 · AlternativoEl principal falló; se recurre a otro modelo.Respuesta, quizá más sencilla.
3 · Caché / FAQNo hay ningún modelo disponible.Respuesta preparada para preguntas frecuentes.
4 · ColaNo es posible responder ahora.«Registramos tu solicitud; responderemos pronto.»
5 · PersonaTema delicado o fallo prolongado.Derivación a una persona.

💡 Consejo

Empieza de forma sencilla: en el gateway del tema 3, registra una línea JSON por llamada en un archivo ({"trace": …, "tarea": …, "modelo": …, "ms": …, "tokens_in": …, "tokens_out": …, "ok": …}). Con eso ya puedes crear un panel de costos y latencia. No registres el texto completo de conversaciones con datos personales; guarda lo necesario para depurar durante un tiempo definido.

🧩 Términos nuevos

Trace: el rastro de una solicitud a través de todas sus etapas, vinculado por un mismo identificador. Span: cada etapa dentro del trace (buscar contexto, llamar al modelo, validar). Eval: un conjunto fijo de preguntas con respuestas esperadas, que se ejecuta con cada cambio de prompt o modelo para comprobar si bajó la calidad.

Por qué aprender

Los modelos se equivocan de forma silenciosa: la respuesta está bien escrita, pero es incorrecta, y no aparece ninguna excepción en el registro. Sin observabilidad, solo te enteras por el cliente. Y sin niveles de degradación, la caída de un proveedor externo se convierte en la caída de todo tu producto.
