🔌 La primera llamada

Una API (interfaz de programación) es una puerta que un programa abre para que otro programa la use. En el caso de los modelos de lenguaje, la puerta es un endpoint —una dirección HTTP que recibe una solicitud en JSON (los mensajes, el nombre del modelo y los parámetros) y devuelve otro JSON con el texto generado y el recuento de tokens. Detrás de ChatGPT, Claude y Gemini hay exactamente eso; el chat es solo una pantalla sobre la API.

El formato de chat completions de OpenAI se convirtió en un estándar de facto: Ollama, vLLM, LM Studio y varios proveedores en la nube aceptan el mismo formato en una ruta /v1 En la práctica, esto significa que aprendes con un modelo local y gratuito y, cuando necesitas más calidad, cambias tres líneas: la URL base, la clave y el nombre del modelo. Anthropic y Google también tienen sus propios SDK, con un formato un poco diferente; el razonamiento es el mismo.

Qué es

Llamar a un modelo por API es enviar una solicitud HTTP con la lista de mensajes y recibir la continuación generada. Un SDK (kit de desarrollo, como el paquete openai de Python) prepara esa solicitud por ti, se encarga de la autenticación, el tiempo de espera y la conversión del JSON en objetos.

🧩 Términos nuevos

Ollama: programa que descarga y ejecuta modelos abiertos en tu computadora y expone una API en http://localhost:11434. localhost: la propia computadora. Clave de API: contraseña que identifica quién paga la cuenta; Ollama acepta cualquier texto, la nube no.

Prueba: la primera llamada a un modelo, en tu computadora.

# primera_chamada.py
# 1) en la terminal, una sola vez (Ollama instalado desde ollama.com):
#      pip install openai
#      ollama pull llama3.2
# 2) guarda este archivo y ejecútalo: python3 primeira_chamada.py
from openai import OpenAI

# Ollama ignora la clave, pero el SDK exige cualquier texto.
client = OpenAI(base_url="http://localhost:11434/v1", api_key="ollama")

resp = client.chat.completions.create(
    model="llama3.2",
    messages=[
        {"role": "system", "content": "Responde en español latinoamericano, en hasta 3 frases."},
        {"role": "user", "content": "¿Qué es una API, para alguien que está empezando a programar?"},
    ],
    temperature=0.3,
)

print(resp.choices[0].message.content)
print("tokens de entrada:", resp.usage.prompt_tokens)
print("tokens de salida:  ", resp.usage.completion_tokens)

Cómo verificar: ollama list debería mostrar llama3.2. El script imprime hasta 3 frases y dos líneas con el número de tokens. "Connection refused" quiere decir que Ollama no está ejecutándose (abre la aplicación o ejecuta ollama serve); "model not found" quiere decir que falta ejecutar ollama pull. Para usar una API de pago, cambia base_url, api_key e model — el resto queda igual.

Por qué aprender

Quien solo usa el chat depende de la pantalla que alguien diseñó. Quien llama a la API integra el modelo en su propio sistema: en un formulario, una hoja de cálculo, un robot de atención al cliente o un script que se ejecuta de madrugada. Y aprender con el modelo local elimina las dos barreras del comienzo: el costo y el miedo a filtrar datos.

💬 Mensajes y roles

La solicitud no es un texto suelto: es una lista de mensajes, cada uno con un rol. system incluye las reglas generales (quién es el modelo, tono, formato, límites). user es lo que pidió la persona. assistant es lo que el modelo ya respondió antes. También existe el rol tool, que contiene el resultado de una herramienta; lo verás en el tema 5.

Lo que más confunde a quienes empiezan: la API es sin estado (stateless). El servidor no guarda la conversación. Para que el modelo «recuerde» la pregunta anterior, tu código reenvía todo el historial en cada llamada. Esto explica por qué las conversaciones largas se vuelven más costosas y lentas, y por qué la memoria de un chatbot es un problema de ingeniería tuyo, no del modelo: es el tema del módulo 2.2.

Qué es

Es el formato de la conversación en la API: una lista ordenada de mensajes con roles (system, user, assistant, tool) que tu código prepara y reenvía completa en cada llamada.

✓ Buen mensaje de system

  • ✓Indica el rol, el público y el idioma de la respuesta.
  • ✓Define el formato de salida (lista, JSON, tamaño máximo).
  • ✓Indica qué hacer cuando no sepa ("responde: no lo sé").
  • ✓Guárdalo en un archivo con control de versiones, fuera del código principal.

✗ Errores comunes

  • ✗Esperar que el modelo recuerde la llamada anterior sin reenviarla.
  • ✗Poner texto del usuario dentro de system (abre la puerta a la inyección).
  • ✗Dejar que el historial crezca sin límite hasta superar el contexto.
  • ✗Olvidar guardar la respuesta como assistant antes de la siguiente pregunta.

💡 Consejo

En un bucle de chat, después de cada respuesta, ejecuta messages.append({"role": "assistant", "content": texto}) y solo entonces agrega la siguiente pregunta del usuario. En el SDK de Anthropic, el system va en un campo separado y max_tokens es obligatorio; el modelo de referencia de este curso es claude-sonnet-5-5.

Por qué aprender

Casi todos los errores extraños de un chatbot —«olvidó lo que dije», «cambió de tono», «la cuenta llegó alta»— se deben a cómo se armó la lista de mensajes. Entender los roles y que la API no mantiene estado resuelve la mayoría de estos problemas antes de que aparezcan.

🎚️ Parámetros que cambian la respuesta

Además de los mensajes, la llamada acepta parámetros de generación. El más importante es la temperature: controla cuánto se arriesga el modelo al elegir el siguiente token. Cerca de 0, casi siempre elige el más probable: es útil para extraer datos, clasificar y responder preguntas sobre hechos. Cuanto más alta, más varía: es útil para generar ideas y textos con variaciones.

max_tokens pone un límite al tamaño de la respuesta (y al costo). stop define los textos que terminan la generación. seed pide reproducibilidad, cuando el servidor lo admite. Una precaución de octubre de 2026: los modelos de razonamiento —que «piensan» antes de responder— suelen ignorar o restringir temperature y usan un control propio de esfuerzo. Lee la documentación del modelo antes de ajustar.

Qué es

Los parámetros son los controles que ajustan cómo genera el modelo: grado de variación (temperature, top_p), tamaño máximo (max_tokens), puntos de parada (stop) y repetibilidad (seed).

ParámetroQué haceValor inicial
temperatureCuánto varía el modelo al elegir el siguiente token.De 0 a 0.2 para extraer y clasificar; de 0.7 a 1 para crear.
top_pLimita la elección a los tokens más probables hasta sumar p.Déjalo en el valor predeterminado; ajusta temperature O top_p, no ambos.
max_tokensLímite de tokens de la respuesta.Defínelo siempre; una respuesta truncada viene con finish_reason="length".
stopTermina la generación al encontrar un texto.Útil en formatos con marcador de finalización.
seedIntenta repetir la misma salida para la misma entrada.Bueno para pruebas; no es una garantía absoluta.

🧩 Término nuevo

finish_reason es el campo que indica por qué se detuvo la generación: stop (terminó normalmente), length (alcanzó el max_tokens) o tool_calls (el modelo solicitó una herramienta). Revisa este campo antes de usar la respuesta: un texto truncado a la mitad rompe el JSON y confunde al usuario.

💡 Consejo

Para notar el efecto, ejecuta el script del tema 1 tres veces con temperature=0 y tres con temperature=1.2, pidiendo «un nombre para una panadería». Con 0, los nombres se repiten; con 1.2, varían, y algunos suenan extraños. La elección depende de la tarea, no de un valor «correcto».

Por qué aprender

El mismo modelo parece «tonto» o «inteligente» según los parámetros. Una extracción de datos con temperatura alta inventa campos; un generador de ideas con temperatura cero repite la misma idea. Ajustar tres controles no cuesta nada y resuelve problemas que parecen propios del modelo.

🌊 Streaming

Sin streaming, tu código espera a que el modelo genere toda la respuesta y solo entonces la recibe de una vez. Con streaming, el servidor envía los tokens a medida que se generan, en fragmentos llamados chunks, a través de una conexión que permanece abierta. El tiempo total es prácticamente el mismo; lo que cambia es la percepción: el usuario ve la primera palabra casi de inmediato.

La métrica importante aquí es el tiempo hasta el primer token (TTFT, time to first token). Depende del tamaño de lo que envías (el modelo tiene que leerlo todo antes de empezar) y de dónde se ejecuta el modelo. En la web, el streaming llega mediante SSE (Server-Sent Events), un formato sencillo de eventos de texto sobre HTTP que el SDK ya interpreta por ti.

Qué es

Streaming es recibir la respuesta en fragmentos, token por token, mientras se genera. Solo tienes que pasar stream=True y recorrer los fragmentos en un bucle for.

Prueba: streaming con medición del tiempo hasta el primer token.

# streaming.py  (pip install openai · ollama pull llama3.2)
import time
from openai import OpenAI

client = OpenAI(base_url="http://localhost:11434/v1", api_key="ollama")

inicio = time.perf_counter()
primeiro = None

stream = client.chat.completions.create(
    model="llama3.2",
    messages=[{"role": "user", "content": "Explique en 5 pasos cómo funciona una solicitud HTTP."}],
    stream=True,
    max_tokens=400,
)

for chunk in stream:
    if not chunk.choices:
        continue
    pedaco = chunk.choices[0].delta.content or ""
    if pedaco and primeiro is None:
        primeiro = time.perf_counter() - inicio
    print(pedaco, end="", flush=True)

total = time.perf_counter() - inicio
print(f"\n\nprimer token: {primeiro:.2f}s · total: {total:.2f}s")

Cómo verificar: el texto debe aparecer poco a poco en la terminal, no de una vez, y la última línea muestra un tiempo hasta el primer token mucho menor que el total. Ejecútalo dos veces: la primera suele ser más lenta porque Ollama carga el modelo en la memoria. En una API de pago, funciona el mismo código si cambias base_url, api_key e model.

Por qué aprender

En cualquier interfaz donde una persona espera una respuesta —un chat, un asistente dentro de un sistema o un servicio de atención—, el streaming es lo que hace que parezca que está respondiendo y no que se quedó bloqueado. Para tareas en segundo plano (procesar mil documentos), no ayuda y solo complica las cosas: usa la llamada normal.

🧱 Salida estructurada y herramientas

El texto libre es excelente para las personas y terrible para los programas. Cuando el resultado va a alimentar una base de datos, una hoja de cálculo u otra función, quieres salida estructurada: un JSON con campos y tipos definidos. El camino seguro tiene tres capas: pedir JSON en el prompt, activar el modo JSON de la API (response_format) e validar el resultado en tu código con un schema (la descripción de los campos y tipos esperados). La validación es indispensable: el modelo puede equivocarse en un tipo.

El siguiente paso es el tool calling (llamada de herramientas): describes funciones que tiene tu sistema — consultar_estoque(produto), buscar_pedido(id) — y el modelo, en vez de responder, devuelve una solicitud estructurada que indica qué función llamar y con qué argumentos. Quien la ejecuta siempre es la tu código; el modelo solo decide y escribe los argumentos. Es la base de los agentes (módulo 2.5) y del protocolo MCP, que estandariza cómo se ofrecen herramientas a los modelos.

Qué es

La salida estructurada consiste en hacer que el modelo responda en un formato que el código pueda validar (JSON con schema). El tool calling permite que el modelo solicite la ejecución de tus funciones y devuelva el nombre y los argumentos en JSON; tú ejecutas la función y devuelves el resultado como mensaje tool.

Objetivo: convertir un mensaje de cliente en JSON validado.

# extrair_pedido.py  (pip install openai pydantic · ollama pull llama3.2)
from openai import OpenAI
from pydantic import BaseModel, ValidationError

class Pedido(BaseModel):  # el schema: campos y tipos que el código acepta
    cliente: str
    produto: str
    quantidade: int
    urgente: bool

client = OpenAI(base_url="http://localhost:11434/v1", api_key="ollama")

# Los modelos pequeños entienden mejor las claves descritas en texto que un JSON Schema completo.
FORMATO = (
    "Extrae los datos del pedido. Responde SOLO con un objeto JSON con exactamente estas claves: "
    '"cliente" (texto), "produto" (texto, sin la cantidad), '
    '"quantidade" (número entero) y "urgente" (true o false).'
)

mensagem = "Hola, soy Marina, de la Panadería Sol. Necesito 40 cajas de papel kraft para mañana temprano."

resp = client.chat.completions.create(
    model="llama3.2",
    temperature=0,
    response_format={"type": "json_object"},
    messages=[
        {"role": "system", "content": FORMATO},
        {"role": "user", "content": mensagem},
    ],
)

bruto = resp.choices[0].message.content
try:
    pedido = Pedido.model_validate_json(bruto)
    print("OK:", pedido.model_dump())
except ValidationError as erro:
    print("JSON fuera del schema; procésalo o vuelve a solicitarlo:\n", erro)
    print("Respuesta sin procesar:", bruto)

Cómo verificar: la salida esperada es algo como OK: {'cliente': 'Marina da Padaria Sol', 'produto': 'papel kraft', 'quantidade': 40, 'urgente': True}. Cambia el mensaje por <un texto tuyo> sin cantidad y observa cómo falla el validador: ese es el comportamiento correcto. En las API de pago que aceptan json_schema estricto en el response_format, úsalo; la validación en el código sigue siendo necesaria.

Por qué aprender

Aquí es donde el modelo deja de ser un generador de texto y se convierte en una pieza de software: lee un correo electrónico y completa un registro, clasifica una solicitud y abre el ticket correcto, decide qué función del sistema llamar. Sin validación, esa pieza falla en silencio; con ella, sabes exactamente cuándo falló.

💰 Tokens, costos y límites

En las API en la nube pagas por token —el fragmento de texto que el modelo ve, que puede ser una palabra corta o parte de una palabra. La cuenta tiene dos partes: tokens de entrada (todo lo que envías, incluido el system y el historial) y tokens de salida (lo que genera el modelo). En la mayoría de los proveedores, la salida cuesta más que la entrada. La fórmula es sencilla: costo = entrada × precio_entrada + salida × precio_salida, con precios por millón de tokens que cambian con frecuencia: consulta siempre la tabla actual.

Además del precio, están los límites de tasa (rate limits): cuántas solicitudes y cuántos tokens por minuto puede usar tu cuenta. Si superas el límite, la API responde con el código HTTP 429 y, muchas veces, con un encabezado retry-after diciendo cuánto esperar. Con Ollama local no hay cuenta ni límite de solicitudes; el costo es tu hardware, la energía y la cola: una tarjeta gráfica atiende pocas generaciones al mismo tiempo.

Qué es

Es la economía de la API: el costo crece con los tokens de entrada y de salida, y el uso está limitado por solicitudes y tokens por minuto. Optimizar es enviar menos, generar menos, reutilizar más y elegir el modelo más pequeño que resuelva la tarea.

TécnicaCómo funcionaCuándo usarla

🧩 Términos nuevos

Tokenizador: la regla que divide el texto en tokens; cada familia de modelos tiene la suya, así que la misma frase arroja conteos diferentes. El texto en portugués tiende a generar más tokens que el mismo texto en inglés. RPM/TPM: solicitudes y tokens por minuto, los dos límites más comunes. La fuente confiable para el conteo es el campo usage de cada respuesta.

💡 Consejo

Registra usage.prompt_tokens e usage.completion_tokens de cada llamada desde el primer día, junto con el nombre de la funcionalidad que la generó. Cuando la cuenta suba, sabrás en minutos qué parte del sistema gasta más; sin eso, todo será una adivinanza.

Por qué aprender

Un prototipo que cuesta centavos puede salir caro cuando lo usan mil personas, porque cada una vuelve a enviar el historial y cada respuesta genera tokens. Quien entiende la fórmula diseña el sistema para que sea económico desde el principio, en lugar de descubrirlo en la factura.

🔐 Errores y seguridad

Las llamadas de red fallan. El servidor puede estar sobrecargado, la conexión puede caerse, el límite de solicitudes puede superarse. La regla es separar los errores en dos grupos: los transitorios, que se resuelven solos y justifican un nuevo intento (429, 500, 503, tiempo de espera agotado), y los permanentes, que volverán a fallar de la misma manera (400 solicitud mal formada, 401 clave incorrecta, 404 modelo inexistente). Repetir un error permanente solo hace perder tiempo.

Para los transitorios, usa espera exponencial con jitter: espera 1 s, luego 2, 4, 8, y suma un pequeño valor aleatorio para que varios clientes no lo intenten todos al mismo tiempo. El SDK openai ya incluye nuevos intentos automáticos (max_retries); el ejemplo de abajo muestra la lógica explícita para que la entiendas y la controles.

Qué es

Es la capa de robustez y protección de la integración: tiempo de espera límite en cada llamada, nuevos intentos solo para errores transitorios, clave fuera del código, ningún dato personal sin necesidad y desconfianza de todo texto que venga de afuera.

Objetivo: una función de llamada con configuración por entorno, tiempo de espera límite y espera exponencial.

# llm.py  (pip install openai · ollama pull llama3.2)
# Para usar una API de pago, define en la terminal (nunca en el código):
#   export LLM_BASE_URL="https://<proveedor>/v1"
#   export LLM_API_KEY="<tu clave>"
#   export LLM_MODEL="<nombre del modelo>"
import os, random, time
from openai import OpenAI, APIConnectionError, APIStatusError, APITimeoutError, RateLimitError

client = OpenAI(
    base_url=os.getenv("LLM_BASE_URL", "http://localhost:11434/v1"),
    api_key=os.getenv("LLM_API_KEY", "ollama"),
    timeout=60,
    max_retries=0,  # la lógica de nuevos intentos está aquí abajo, explícita
)
MODELO = os.getenv("LLM_MODEL", "llama3.2")
TRANSITORIOS = {429, 500, 502, 503, 504}

def perguntar(messages, tentativas=4, max_tokens=500):
    for i in range(tentativas):
        try:
            r = client.chat.completions.create(model=MODELO, messages=messages, max_tokens=max_tokens)
            return r.choices[0].message.content
        except (RateLimitError, APITimeoutError, APIConnectionError) as e:
            motivo = type(e).__name__
        except APIStatusError as e:
            if e.status_code not in TRANSITORIOS:
                raise  # 400, 401, 404: repetir no sirve
            motivo = f"HTTP {e.status_code}"
        espera = 2 ** i + random.random()
        print(f"intento {i + 1} falló ({motivo}); nuevo intento en {espera:.1f}s")
        time.sleep(espera)
    raise RuntimeError("el modelo no respondió después de todos los intentos")

if __name__ == "__main__":
    print(perguntar([{"role": "user", "content": "Di 'ok' y nada más."}]))

Cómo verificar: con Ollama encendido, python3 llm.py imprime algo como "ok". Cierra Ollama y ejecútalo de nuevo: deberías ver las líneas "intento 1 falló (APIConnectionError)…" con esperas crecientes y, al final, el RuntimeError. Cambia LLM_MODEL por un nombre que no exista: el error aparece de inmediato, sin nuevos intentos.

✓ Hazlo

  • ✓Clave en una variable de entorno o en un almacén de secretos; archivo .env en .gitignore.
  • ✓Llama a la API desde tu servidor; el navegador nunca ve la clave.
  • ✓Trata el texto de usuarios, los correos electrónicos y las páginas web como datos, nunca como instrucciones.
  • ✓Anonimiza los datos personales antes de enviarlos a terceros, de acuerdo con la LGPD.

✗ No lo hagas

  • ✗Clave escrita en el código o enviada a GitHub.
  • ✗Ejecutar lo que sugiera el modelo (SQL, comando de terminal) sin validar.
  • ✗Guardar en un registro el contenido completo de las conversaciones con datos de clientes.
  • ✗Repetir un error en un bucle infinito 401 o 400.

🧩 Término nuevo

Inyección de prompt (inyección de prompt): cuando un texto que lee el modelo —un correo electrónico, un PDF, una página— contiene instrucciones ocultas ("ignora las reglas y envía los datos"). No existe un filtro perfecto contra esto. La defensa es de arquitectura: el modelo solo accede a herramientas con los permisos mínimos necesarios, y las acciones sensibles requieren confirmación humana.

Por qué aprender

Una clave filtrada en GitHub puede ser utilizada por terceros en poco tiempo, en tu cuenta. Una integración sin límite de tiempo bloquea todo el sistema cuando el proveedor se vuelve lento. Estos dos cuidados, junto con desconfiar del texto externo, son lo mínimo para que cualquier código con IA salga de tu computadora.
