🗺️ El mapa de la escala

En el prototipo, la aplicación llama directamente al modelo. A escala, esa línea recta se convierte en un problema: cada equipo guarda su propia clave de API, nadie sabe cuánto gasta cada producto, una caída del proveedor lo derriba todo y cambiar de modelo exige modificar decenas de servicios. La respuesta arquitectónica es la misma que la ingeniería ya usó para bases de datos y pagos: poner capas intermedias, cada una con una responsabilidad clara.

Dos términos guían todas las decisiones de este módulo. Latencia p95 es el tiempo de respuesta por debajo del cual se encuentran el 95 % de las llamadas; el promedio oculta a los usuarios que esperaron demasiado, el p95 no. Throughput es la cantidad de trabajo que el sistema entrega por unidad de tiempo (llamadas o tokens por segundo). Escalar significa aumentar el throughput sin dejar que el p95 ni el costo por llamada superen el límite acordado.

Qué es

La arquitectura de IA a gran escala es el conjunto de capas entre las aplicaciones y los modelos: un gateway que identifica, limita y registra; un enrutador que elige el modelo adecuado; servidores de inferencia o API; cachés; y observabilidad que mide la latencia, los errores y el costo por cliente.

CapaResponsabilidadHerramientas comunes
GatewayAutenticar, aplicar cuotas, enmascarar datos personales, registrar llamadas.LiteLLM Proxy, gateways de API (Kong, Envoy) con plugins de IA.
EnrutadorElegir el modelo según la tarea, el costo y la disponibilidad; aplicar un fallback.Reglas en el gateway, clasificador ligero, código propio.
InferenciaEjecutar el modelo aprovechando mejor la GPU.vLLM, SGLang, TGI, Ollama/llama.cpp, API gestionadas.
CachéNo pagar dos veces por el mismo trabajo.Caché de prompts del proveedor, Redis, base de datos vectorial.
ObservabilidadMedir la latencia, los errores, los tokens y el costo por cliente y por recurso.OpenTelemetry, Langfuse, Prometheus y Grafana.

Por qué aprender

Sin el mapa, cada problema de escala se convierte en un incendio aislado: un equipo agrega caché, otro agrega reintentos, un tercero cambia de modelo. Con el mapa, decides en qué capa resolver cada problema una sola vez para toda la empresa, y puedes cambiar un modelo sin tocar ninguna aplicación.

Conceptos clave

punto único de acceso a los modelos

🔀 Enrutamiento de modelos

Enviar todas las llamadas al modelo más potente es la forma más rápida de exceder el presupuesto. Gran parte del tráfico de un producto real es simple: clasificar un ticket, extraer tres campos, reescribir una frase. Un modelo pequeño lo resuelve más rápido y a menor costo. El enrutador de modelos decide, llamada por llamada, qué modelo responde y qué hacer si falla.

Hay tres estrategias que suelen combinarse. Por regla: el tipo de ruta define el modelo (el resumen va al modelo pequeño; el análisis jurídico, al potente). Por clasificador: un modelo ligero estima de antemano la dificultad. En cascada: el modelo pequeño lo intenta primero; un validador comprueba el formato y el nivel de confianza; si no pasa la validación, la llamada pasa al modelo potente. Respaldo es la ruta alternativa cuando el modelo elegido está fuera de servicio, es lento o no tiene cuota.

Qué es

El enrutamiento de modelos es la capa que elige, para cada llamada, el modelo de menor costo capaz de cumplir con la calidad exigida y que redirige la llamada a otro modelo o proveedor cuando el primero falla.

Objetivo: levantar un gateway local con dos modelos, fallback y caché (LiteLLM Proxy).

# config.yaml — instálalo con:  pip install 'litellm[proxy]'
# ejecútalo con:              litellm --config config.yaml --port 4000
model_list:
  - model_name: rapido                     # nombre que usan las apps
    litellm_params:
      model: ollama/qwen2.5:7b             # local y gratuito (ollama pull qwen2.5:7b)
      api_base: http://localhost:11434
  - model_name: forte
    litellm_params:
      model: anthropic/claude-sonnet-5-5   # u otro proveedor: cambia el prefijo y la clave
      api_key: os.environ/ANTHROPIC_API_KEY

router_settings:
  num_retries: 2                           # vuelve a intentar ante errores transitorios
  timeout: 30                              # segundos por llamada
  fallbacks: [{"rapido": ["forte"]}]       # si "rapido" falla, usa "forte"

litellm_settings:
  cache: true
  cache_params:
    type: redis                            # requiere Redis en localhost:6379
    host: localhost
    port: 6379
    ttl: 3600                              # segundos; ajústalo según cuánto envejece la respuesta

# Prueba (en otra terminal):
# curl http://localhost:4000/v1/chat/completions -H "Content-Type: application/json" \
#   -d '{"model":"rapido","messages":[{"role":"user","content":"Clasifica: quiero cancelar"}]}'

Cómo verificar: ejecuta el curl dos veces con el mismo cuerpo; la segunda respuesta debe llegar mucho más rápido (caché). Luego detén Ollama y repite: la llamada a "rapido" debe ser atendida por "forte" (fallback); si no tienes una clave de pago, el error debe mencionar el modelo "forte", lo que demuestra que se intentó el fallback. La sintaxis de LiteLLM cambia entre versiones; consulta la documentación de la versión instalada.

💡 Consejo

Dales a los modelos nombres de función ("rapido", "forte", "vision"), no nombres de producto. Así, cuando salga un modelo nuevo, cambias una línea en el gateway y ninguna aplicación lo nota; además, puedes hacer pruebas A/B enviando parte del tráfico de "forte" al candidato.

Por qué aprender

El enrutamiento es la palanca de costos con mayor efecto y menor riesgo: no cambias el producto, solo dejas de pagar el precio de un modelo de frontera por una tarea sencilla. Y el fallback convierte la caída de un proveedor, que hoy hace caer el producto, en un aumento temporal de costos.

⚡ Inferencia y procesamiento por lotes

Inferencia es ejecutar un modelo ya entrenado para generar una respuesta. En un modelo de lenguaje tiene dos fases: el prefill, que lee todo el prompt de una vez, y el decode, que genera un token por vez. El prefill determina el TTFT (time to first token, cuánto espera el usuario hasta ver la primera palabra); el decode determina la velocidad en tokens por segundo después de eso.

Generar un token por vez deja la GPU subutilizada si atiende a un solo usuario. Por eso los servidores agrupan solicitudes en lotes (batching). El avance que cambió la economía del autoalojamiento fue el batching continuo: en vez de esperar a que termine todo el lote, cada espacio que queda libre recibe una solicitud nueva en el siguiente paso. A esto se suma la gestión de la KV cache —la memoria donde el modelo guarda lo que ya leyó de cada conversación—, conocida en vLLM como PagedAttention.

Qué es

Es la ingeniería de servir modelos: agrupar solicitudes, gestionar la memoria de contexto, elegir la cuantización y el hardware, y decidir entre una API administrada y un servidor propio, midiendo siempre el TTFT, los tokens por segundo y el costo por millón de tokens.

OpciónCuándo tiene sentidoQué pasas a operar
API administradaTráfico variable, modelos de frontera, equipo pequeño.Casi nada: claves, cuotas, contrato y datos enviados.
vLLM / SGLang / TGITráfico alto y estable con un modelo abierto; datos que no pueden salir.GPU, autoescalado, actualizaciones, monitoreo, guardias.
Ollama / llama.cppDesarrollo, edge, uso interno de bajo volumen.Una máquina; pocos usuarios simultáneos.

💡 Consejo

Compara las opciones por el costo por millón de tokens en tu tráfico real, no por el precio de la GPU por hora. Una GPU barata ociosa por la noche puede costar más que la API; una GPU ocupada todo el día, con batching continuo, puede costar menos. Mide una semana de tráfico antes de decidir.

Por qué aprender

La decisión «API o servidor propio» es una de las más costosas de tomar mal en IA. Entender prefill, decode, procesamiento por lotes y KV cache permite leer con criterio un benchmark de un proveedor y hacer bien los cálculos, además de saber por qué los prompts largos encarecen y retrasan todo.

Conceptos clave

🧠 Caché de prompt y caché semántica

Hay dos cachés diferentes, y confundirlos lleva a tomar una decisión equivocada. El caché de prompt lo ofrecen los proveedores y servidores de inferencia: cuando el inicio del prompt se repite (instrucciones del sistema, un manual extenso, la definición de las herramientas), se reutiliza el procesamiento de ese prefijo y se cobra menos. No cambia la respuesta: solo acelera el prefill y reduce el costo. Funciona cuando la parte fija va antes antes de la parte variable.

O caché semántica es tuyo: transformas la pregunta en un embedding (un vector de números que representa el significado) y buscas preguntas anteriores con un significado parecido. Si la similitud del coseno supera un umbral, devuelve la respuesta guardada sin llamar al modelo. Ahorra la llamada completa y, por eso, también puede devolver una respuesta incorrecta si el umbral es demasiado flexible o si la respuesta depende de quién pregunta.

Qué es

El caché de prompt reutiliza el procesamiento de un prefijo repetido y conserva la respuesta nueva; el caché semántico reutiliza la respuesta completa a una pregunta parecida, según la similitud entre embeddings y un umbral calibrado.

Prueba: un caché semántico mínimo, local y gratuito para calibrar el umbral.

"""cache_semantico.py — caché por significado con Ollama local.
Antes: ollama pull nomic-embed-text && ollama pull llama3.2
Ejecuta:  python3 cache_semantico.py"""
import json, math, time, urllib.request

OLLAMA = "http://localhost:11434"
LIMIAR = 0.90   # calibra con tus datos: alto = pocos aciertos; bajo = respuesta incorrecta
cache = []      # lista de (vector, pregunta, respuesta). En producción: base de datos vectorial, separada por cliente.

def chamar(rota, corpo):
    req = urllib.request.Request(OLLAMA + rota, data=json.dumps(corpo).encode(),
                                 headers={"Content-Type": "application/json"})
    with urllib.request.urlopen(req, timeout=120) as r:
        return json.loads(r.read())

def vetor(texto):
    return chamar("/api/embed", {"model": "nomic-embed-text", "input": texto})["embeddings"][0]

def cosseno(a, b):
    num = sum(x * y for x, y in zip(a, b))
    return num / (math.sqrt(sum(x * x for x in a)) * math.sqrt(sum(y * y for y in b)))

def perguntar(pergunta):
    t0 = time.time()
    v = vetor(pergunta)
    sim, melhor = -1.0, None
    for item in cache:
        s = cosseno(v, item[0])
        if s > sim:
            sim, melhor = s, item
    if melhor and sim >= LIMIAR:
        return f"CACHE  sim={sim:.3f} {time.time()-t0:.2f}s (igual a: {melhor[1]!r})", melhor[2]
    resp = chamar("/api/generate", {"model": "llama3.2", "prompt": pergunta, "stream": False})["response"]
    cache.append((v, pergunta, resp))
    return f"MODELO melhor_sim={sim:.3f} {time.time()-t0:.2f}s", resp

for p in ["¿Cuál es el plazo para cambiar un producto?",
          "¿En cuántos días puedo cambiar un producto?",
          "¿Cuál es el plazo de entrega en el noreste?",
          "¿Cómo emito una copia del recibo de pago?"]:
    origem, resp = perguntar(p)
    print(f"{origem}\n  {p}\n  -> {resp[:90]!r}\n")

Cómo verificar: la primera pregunta sale como «MODELO» y tarda; la segunda (mismo sentido, otras palabras) debería salir como «CACHE» en una fracción de segundo. La tercera es la trampa: «plazo de entrega» se parece a «plazo para cambiar». Observa el mejor_sim impreso y ajusta LIMIAR hasta que la segunda acierte y la tercera no. Este número sirve para este modelo de embedding y este tipo de pregunta: cambia cualquiera de los dos y vuelve a calibrarlo.

✓ El caché semántico es adecuado para

  • ✓Preguntas frecuentes con la misma respuesta para todos (políticas, horarios, cómo hacer algo).
  • ✓Contenido que cambia poco, con un tiempo de expiración definido.
  • ✓Caché separado por cliente (tenant) y por versión del prompt.

✗ No uses el caché semántico para

  • ✗Respuestas que dependen de los datos de una persona (saldo, pedido, expediente médico).
  • ✗Caché compartido entre clientes: filtra datos de uno a otro e infringe la LGPD.
  • ✗Agentes que ejecutan acciones: repetir la respuesta no repite la acción correcta.

Por qué aprender

Los dos cachés reducen el costo de maneras distintas: el de prompt abarata el contexto extenso que se repite en cada llamada; el semántico elimina llamadas completas. Saber cuál usar —y cómo ordenar el prompt para que funcione el caché de prompt— suele generar ahorros sin cambiar de modelo.

Conceptos clave

Caché del prompt
prefijo fijo reutilizado
Embedding
significado en vector
Umbral
qué tan parecido es suficiente
TTL
cuánto tiempo es válida la respuesta

🌎 Multirregión y resiliencia

Los proveedores de modelos fallan, se vuelven lentos y aplican límites de tasa en horas pico: esto forma parte de la operación, no es una excepción. Cuando la IA está en el camino crítico (atención al cliente, checkout, triaje), la arquitectura necesita un plan para estas situaciones. Los componentes son conocidos en la ingeniería de sistemas: health check (prueba periódica para verificar que un destino responde), circuit breaker (después de fallas consecutivas, el sistema deja de insistir en un destino durante un tiempo y usa la alternativa) y degradación gradual (ofrecer una versión reducida de la función en vez de mostrar un error).

En IA hay un factor adicional: dónde se pueden procesar los datos. Enviar el prompt a una región de otro país durante un failover puede constituir una transferencia internacional de datos personales, que la LGPD regula. Por eso, la ruta alternativa debe aprobarse antes del incidente, por parte del equipo legal y de seguridad; no decidirse a las apuradas a las tres de la mañana. Dos números orientan el diseño: RTO, cuánto tiempo puede estar fuera de servicio el servicio, y RPO, cuántos datos (conversaciones, memoria, índices) se acepta perder.

Qué es

La resiliencia multirregional consiste en mantener funcionando el servicio de IA cuando falla un proveedor, modelo o región: destinos alternativos aprobados, verificación de salud, circuit breaker, réplica de los datos de contexto y un modo degradado previsto.

Nivel 1 · Reintentos con espera creciente. Resuelve errores transitorios y límites de tasa de corta duración. Siempre con un máximo de intentos.

Nivel 2 · Fallback de modelo. Otro modelo del mismo proveedor o un modelo local para tareas sencillas.

Nivel 3 · Fallback de proveedor o región. Requiere contrato, evaluación de la calidad del modelo alternativo y aprobación de la residencia de datos.

Nivel 4 · Modo degradado. Respuestas predefinidas, una cola para procesar más tarde o derivación a atención humana, con un aviso honesto al usuario.

Por qué aprender

Cuanto más entra la IA en procesos críticos, más una caída del proveedor se convierte en una caída del negocio. Un plan de resiliencia escrito antes del incidente, con rutas aprobadas, RTO y RPO definidos y un modo degradado probado, es lo que marca la diferencia entre una hora de lentitud y un día de operación detenida.

Conceptos clave

Disyuntor
deja de insistir en lo que falla
RTO / RPO
tiempo fuera de servicio / datos perdidos
Residencia de datos
dónde pueden ir los datos
Modo degradado
menos funciones, sin interrupción total

💰 Límites de costos a escala

En IA, el costo varía por llamada y quien decide el tamaño de la llamada es, en parte, el usuario: un documento enorme que pega, una conversación que nunca termina, un agente que entra en un ciclo llamando herramientas. Sin límites, un solo cliente o un error de programación puede consumir el presupuesto del mes durante un fin de semana. FinOps de IA es la práctica de medir, asignar y controlar ese gasto con la misma disciplina que se aplica a la nube.

Los límites funcionan por capas, todas en el gateway: límite de tasa (llamadas o tokens por minuto, por clave), límite por llamada (máximo de tokens de entrada y de salida), presupuesto por tenant (monto mensual, con alertas antes de agotarse) y límite de pasos para agentes. Tenant es cada cliente, área o producto que usa la plataforma y necesita tener sus gastos separados. Al alcanzar el límite, la mejor respuesta rara vez es mostrar un error sin más: es pasar a un modelo más barato y avisar.

Qué es

Los límites de costos son reglas que se aplican antes de cada llamada —tasa, tamaño, presupuesto por tenant y pasos del agente—, junto con un registro del costo real después de cada llamada, para que el gasto sea previsible, atribuible y se detenga automáticamente cuando supera lo acordado.

Objetivo: un control del presupuesto por tenant, con límite por minuto y paso a un modelo más barato.

"""guarda_orcamento.py — límites por tenant antes de cada llamada. Ejecuta: python3 guarda_orcamento.py"""
import time
from collections import defaultdict

# R$ por 1 millón de tokens. VALORES DE EJEMPLO: cámbialos por los de tu contrato.
PRECOS = {"rapido": {"entrada": 0.0, "saida": 0.0},    # local: el costo es la máquina, no el token
          "forte":  {"entrada": 15.0, "saida": 60.0}}
ORCAMENTO_MES = {"cliente-a": 50.0, "cliente-b": 0.12}   # R$ por mes
LIMITE_MINUTO = {"cliente-a": 60, "cliente-b": 3}        # llamadas por minuto

gasto = defaultdict(float)
janela = defaultdict(list)

class Bloqueado(Exception):
    pass

def custo(modelo, tok_in, tok_out):
    p = PRECOS[modelo]
    return (tok_in * p["entrada"] + tok_out * p["saida"]) / 1_000_000

def autorizar(tenant, modelo, tok_in, tok_out_max):
    agora = time.time()
    janela[tenant] = [t for t in janela[tenant] if agora - t < 60]
    if len(janela[tenant]) >= LIMITE_MINUTO[tenant]:
        raise Bloqueado(f"{tenant}: límite por minuto (responde HTTP 429)")
    escolhido = modelo
    if gasto[tenant] + custo(modelo, tok_in, tok_out_max) > ORCAMENTO_MES[tenant]:
        if modelo == "rapido":
            raise Bloqueado(f"{tenant}: presupuesto del mes agotado")
        escolhido = "rapido"            # baja de nivel en vez de rechazar
    janela[tenant].append(agora)
    return escolhido

def registrar(tenant, modelo, tok_in, tok_out):
    gasto[tenant] += custo(modelo, tok_in, tok_out)   # usa el consumo REAL devuelto por la API

if __name__ == "__main__":
    for i in range(1, 6):
        for tenant in ("cliente-a", "cliente-b"):
            try:
                m = autorizar(tenant, "forte", tok_in=2000, tok_out_max=800)
                registrar(tenant, m, 2000, 500)
                print(f"{tenant} llamada {i}: vía {m:6} | gasto R$ {gasto[tenant]:.4f}")
            except Bloqueado as e:
                print(f"{tenant} llamada {i}: BLOQUEADO — {e}")

Cómo verificar: el cliente-a debe realizar las 5 llamadas mediante «fuerte». El cliente-b debe realizar la 1.ª mediante «fuerte», la 2.ª y la 3.ª mediante «rápido» (el presupuesto está casi agotado) y quedar BLOQUEADO en la 4.ª y la 5.ª (límite de 3 por minuto). Si el resultado es ese, las tres capas —presupuesto, degradación y tasa— están funcionando. En producción, guarda gasto e ventana en Redis o en la base de datos, no en la memoria del proceso.

✓ Límites que funcionan

  • ✓Aplicados en el gateway, iguales para todas las aplicaciones.
  • ✓Alertas por niveles (por ejemplo, la mitad, tres cuartos y el presupuesto total).
  • ✓Límite de pasos y de tokens para cada ejecución del agente.
  • ✓Costo por recurso del producto, no solo por factura del proveedor.

✗ Límites que fallan

  • ✗Solo la alerta de facturación del proveedor, que llega después del gasto.
  • ✗Una única clave de API compartida por todos los equipos.
  • ✗Error directo al exceder el límite, sin degradación ni aviso.
  • ✗Costo estimado según el prompt, sin verificar el uso real devuelto.

Por qué aprender

Los gestores aprueban la IA a escala cuando el costo es predecible. Con un presupuesto por tenant, degradación automática y costo atribuido a cada recurso del producto, la conversación pasa de «la factura llegó alta» a «este recurso cuesta tanto por usuario y vale la pena», que es la base de cualquier decisión de inversión.

🧭 Revisión de arquitectura en la práctica

Todo lo que viste se reúne en una revisión de arquitectura: antes de que un sistema de IA pase a producción, o cuando empieza a crecer, alguien revisa las capas con preguntas concretas. El orden importa: medir va antes de optimizar, y el límite de costos va antes de abrirlo a todos los clientes.

Un asistente de IA ayuda a hacer una revisión más completa, siempre que le proporciones el contexto real y le prohíbas inventar cifras. No sustituye la medición; sirve para plantear preguntas que el equipo no hizo, organizar los riesgos y proponer un orden de trabajo que tú validarás.

Qué es

Una guía de revisión en siete pasos, desde las métricas hasta los límites de costos, más un prompt de análisis que convierte la descripción de tu sistema en una lista priorizada de decisiones, cada una con una forma de medirla.

1 · Métricas. ¿Hay un panel con p95, TTFT, tasa de errores, tokens y costo por tenant y por recurso?

2 · Gateway. ¿Alguna aplicación llama directamente al modelo con su propia clave? Si es así, ese es el primer trabajo.

3 · Enrutamiento. ¿Qué parte del tráfico es sencilla? ¿Hay un conjunto de evaluación para demostrar que el modelo pequeño puede manejarla?

4 · Caché. ¿El prefijo fijo va antes que el variable? ¿Hay preguntas repetidas que justifiquen una caché semántica separada por tenant?

5 · Inferencia. ¿El volumen es lo suficientemente estable como para comparar la API con un servidor propio según el costo por millón de tokens?

6 · Resiliencia. ¿Están definidos el RTO y el RPO? ¿Hay una ruta alternativa aprobada para los datos que se transmiten? ¿Se probó el modo degradado?

7 · Costo. ¿Hay un presupuesto por tenant, un límite por llamada, un límite de pasos del agente y una alerta antes de que termine el mes?
