🗺️ O mapa da escala

No protótipo, o aplicativo chama o modelo direto. Em escala, essa linha reta vira um problema: cada equipe guarda sua própria chave de API, ninguém sabe quanto cada produto gasta, uma queda do provedor derruba tudo e trocar de modelo exige mexer em dezenas de serviços. A resposta de arquitetura é a mesma que a engenharia já usou para bancos de dados e pagamentos: colocar camadas no meio, cada uma com uma responsabilidade clara.

Dois termos guiam todas as decisões deste módulo. Latência p95 é o tempo de resposta abaixo do qual ficam 95% das chamadas — a média esconde os usuários que esperaram demais, o p95 não. Throughput é quanto trabalho o sistema entrega por unidade de tempo (chamadas ou tokens por segundo). Escalar é aumentar o throughput sem deixar o p95 e o custo por chamada saírem do limite combinado.

O que é

Arquitetura de IA em larga escala é o conjunto de camadas entre os aplicativos e os modelos: um gateway que identifica, limita e registra; um roteador que escolhe o modelo certo; servidores de inferência ou APIs; caches; e observabilidade que mede latência, erro e custo por cliente.

CamadaResponsabilidadeFerramentas comuns
GatewayAutenticar, aplicar cotas, mascarar dados pessoais, registrar chamadas.LiteLLM Proxy, gateways de API (Kong, Envoy) com plugins de IA.
RoteadorEscolher o modelo por tarefa, custo e disponibilidade; fazer fallback.Regras no gateway, classificador leve, código próprio.
InferênciaRodar o modelo com o melhor uso de GPU.vLLM, SGLang, TGI, Ollama/llama.cpp, APIs gerenciadas.
CacheNão pagar duas vezes pelo mesmo trabalho.Cache de prompt do provedor, Redis, banco vetorial.
ObservabilidadeMedir latência, erro, tokens e custo por cliente e por recurso.OpenTelemetry, Langfuse, Prometheus e Grafana.

Por que aprender

Sem o mapa, cada problema de escala vira um incêndio isolado: uma equipe põe cache, outra põe retry, uma terceira troca de modelo. Com o mapa, você decide em que camada cada problema se resolve uma vez, para toda a empresa — e consegue trocar um modelo sem tocar em nenhum aplicativo.

🔀 Roteamento de modelos

Mandar toda chamada para o modelo mais forte é a forma mais rápida de estourar o orçamento. Boa parte do tráfego de um produto real é simples: classificar um ticket, extrair três campos, reescrever uma frase. Um modelo pequeno resolve isso mais rápido e mais barato. O roteador de modelos decide, chamada a chamada, qual modelo atende — e o que fazer se ele falhar.

Há três estratégias, que costumam ser combinadas. Por regra: o tipo de rota define o modelo (resumo vai ao pequeno, análise jurídica ao forte). Por classificador: um modelo leve estima a dificuldade antes. Em cascata: o pequeno tenta primeiro; um validador confere formato e confiança; se não passar, a chamada sobe para o modelo forte. Fallback é a rota alternativa quando o modelo escolhido está fora do ar, lento ou sem cota.

O que é

Roteamento de modelos é a camada que escolhe, para cada chamada, o modelo de menor custo capaz de atender à qualidade exigida, e que redireciona a chamada para outro modelo ou provedor quando o primeiro falha.

Objetivo: subir um gateway local com dois modelos, fallback e cache (LiteLLM Proxy).

# config.yaml — instale com:  pip install 'litellm[proxy]'
# rode com:                   litellm --config config.yaml --port 4000
model_list:
  - model_name: rapido                     # nome que os apps usam
    litellm_params:
      model: ollama/qwen2.5:7b             # local e gratuito (ollama pull qwen2.5:7b)
      api_base: http://localhost:11434
  - model_name: forte
    litellm_params:
      model: anthropic/claude-sonnet-5-5   # ou outro provedor: troque o prefixo e a chave
      api_key: os.environ/ANTHROPIC_API_KEY

router_settings:
  num_retries: 2                           # tenta de novo erros transitórios
  timeout: 30                              # segundos por chamada
  fallbacks: [{"rapido": ["forte"]}]       # se "rapido" falhar, usa "forte"

litellm_settings:
  cache: true
  cache_params:
    type: redis                            # exige Redis em localhost:6379
    host: localhost
    port: 6379
    ttl: 3600                              # segundos; ajuste ao quanto a resposta envelhece

# Teste (outro terminal):
# curl http://localhost:4000/v1/chat/completions -H "Content-Type: application/json" \
#   -d '{"model":"rapido","messages":[{"role":"user","content":"Classifique: quero cancelar"}]}'

Como verificar: rode o curl duas vezes com o mesmo corpo; a segunda resposta deve voltar bem mais rápido (cache). Depois pare o Ollama e repita: a chamada a "rapido" deve ser atendida por "forte" (fallback) — se você não tem chave paga, o erro deve citar o modelo "forte", o que prova que o fallback foi tentado. A sintaxe do LiteLLM muda entre versões; confira a documentação da versão instalada.

💡 Dica

Dê aos modelos nomes de função ("rapido", "forte", "visao"), não nomes de produto. Assim, quando um modelo novo sair, você troca uma linha no gateway e nenhum aplicativo percebe — e consegue fazer testes A/B mandando parte do tráfego de "forte" para o candidato.

Por que aprender

O roteamento é a alavanca de custo com maior efeito e menor risco: você não muda o produto, só para de pagar preço de modelo de fronteira por tarefa simples. E o fallback transforma a queda de um provedor, que hoje derruba o produto, num aumento temporário de custo.

⚡ Inferência e batching

Inferência é rodar um modelo já treinado para gerar uma resposta. Num modelo de linguagem ela tem duas fases: o prefill, que lê o prompt inteiro de uma vez, e o decode, que gera um token por vez. O prefill define o TTFT (time to first token, quanto o usuário espera até ver a primeira palavra); o decode define a velocidade em tokens por segundo depois disso.

Gerar um token por vez deixa a GPU subutilizada se ela atende um usuário só. Por isso os servidores agrupam pedidos em lotes (batching). O avanço que mudou a economia do auto-hospedado foi o batching contínuo: em vez de esperar o lote inteiro terminar, cada vaga liberada recebe um pedido novo no passo seguinte. Junto vem o gerenciamento do KV cache — a memória onde o modelo guarda o que já leu de cada conversa —, que no vLLM ficou conhecido como PagedAttention.

O que é

É a engenharia de servir modelos: agrupar pedidos, gerenciar a memória de contexto, escolher quantização e hardware, e decidir entre API gerenciada e servidor próprio, sempre medindo TTFT, tokens por segundo e custo por milhão de tokens.

OpçãoQuando faz sentidoO que você passa a operar
API gerenciadaTráfego variável, modelos de fronteira, equipe pequena.Quase nada: chaves, cotas, contrato e dados enviados.
vLLM / SGLang / TGITráfego alto e estável com modelo aberto; dados que não podem sair.GPUs, autoescala, atualizações, monitoramento, plantão.
Ollama / llama.cppDesenvolvimento, borda, uso interno de baixo volume.Uma máquina; poucos usuários simultâneos.

💡 Dica

Compare opções pelo custo por milhão de tokens no seu tráfego real, não pelo preço da GPU por hora. Uma GPU barata ociosa à noite pode sair mais cara que a API; uma GPU cheia o dia todo, com batching contínuo, pode sair mais barata. Meça uma semana de tráfego antes de decidir.

Por que aprender

A decisão "API ou servidor próprio" é uma das mais caras de errar em IA. Entender prefill, decode, batching e KV cache permite ler um benchmark de fornecedor com senso crítico e fazer a conta certa — e saber por que prompts longos encarecem e atrasam tudo.

🧠 Cache de prompt e cache semântico

Existem dois caches diferentes, e confundi-los gera decisão errada. O cache de prompt é oferecido pelos provedores e servidores de inferência: quando o começo do prompt se repete (instruções do sistema, um manual longo, a definição das ferramentas), o processamento desse prefixo é reaproveitado e cobrado mais barato. Ele não muda a resposta — só acelera o prefill e reduz custo. Funciona quando a parte fixa vem antes da parte variável.

O cache semântico é seu: você transforma a pergunta num embedding (um vetor de números que representa o significado) e procura perguntas anteriores com significado parecido. Se a similaridade de cosseno passar de um limiar, devolve a resposta guardada sem chamar o modelo. Economiza a chamada inteira — e por isso também pode devolver a resposta errada, se o limiar for frouxo ou se a resposta depender de quem pergunta.

O que é

Cache de prompt reaproveita o processamento de um prefixo repetido e mantém a resposta nova; cache semântico reaproveita a resposta inteira de uma pergunta parecida, decidida por similaridade entre embeddings e um limiar calibrado.

Experimente: um cache semântico mínimo, local e gratuito, para calibrar o limiar.

"""cache_semantico.py — cache por significado com Ollama local.
Antes: ollama pull nomic-embed-text && ollama pull llama3.2
Rode:  python3 cache_semantico.py"""
import json, math, time, urllib.request

OLLAMA = "http://localhost:11434"
LIMIAR = 0.90   # calibre com seus dados: alto = pouco acerto; baixo = resposta errada
cache = []      # lista de (vetor, pergunta, resposta). Em produção: banco vetorial, separado por cliente.

def chamar(rota, corpo):
    req = urllib.request.Request(OLLAMA + rota, data=json.dumps(corpo).encode(),
                                 headers={"Content-Type": "application/json"})
    with urllib.request.urlopen(req, timeout=120) as r:
        return json.loads(r.read())

def vetor(texto):
    return chamar("/api/embed", {"model": "nomic-embed-text", "input": texto})["embeddings"][0]

def cosseno(a, b):
    num = sum(x * y for x, y in zip(a, b))
    return num / (math.sqrt(sum(x * x for x in a)) * math.sqrt(sum(y * y for y in b)))

def perguntar(pergunta):
    t0 = time.time()
    v = vetor(pergunta)
    sim, melhor = -1.0, None
    for item in cache:
        s = cosseno(v, item[0])
        if s > sim:
            sim, melhor = s, item
    if melhor and sim >= LIMIAR:
        return f"CACHE  sim={sim:.3f} {time.time()-t0:.2f}s (igual a: {melhor[1]!r})", melhor[2]
    resp = chamar("/api/generate", {"model": "llama3.2", "prompt": pergunta, "stream": False})["response"]
    cache.append((v, pergunta, resp))
    return f"MODELO melhor_sim={sim:.3f} {time.time()-t0:.2f}s", resp

for p in ["Qual é o prazo para trocar um produto?",
          "Em quantos dias posso trocar um produto?",
          "Qual é o prazo de entrega para o Nordeste?",
          "Como emito a segunda via do boleto?"]:
    origem, resp = perguntar(p)
    print(f"{origem}\n  {p}\n  -> {resp[:90]!r}\n")

Como verificar: a 1ª pergunta sai "MODELO" e demora; a 2ª (mesmo sentido, outras palavras) deve sair "CACHE" em fração de segundo. A 3ª é a armadilha: "prazo de entrega" parece "prazo de troca". Olhe o melhor_sim impresso e ajuste LIMIAR até a 2ª acertar e a 3ª não. Esse número vale para este modelo de embedding e este tipo de pergunta — troque qualquer um e recalibre.

✓ Cache semântico combina com

  • ✓Perguntas frequentes com resposta igual para todos (políticas, horários, como fazer).
  • ✓Conteúdo que muda pouco, com tempo de expiração definido.
  • ✓Cache separado por cliente (tenant) e por versão do prompt.

✗ Não use cache semântico em

  • ✗Respostas que dependem de dados da pessoa (saldo, pedido, prontuário).
  • ✗Cache compartilhado entre clientes: vaza dados de um para outro e fere a LGPD.
  • ✗Agentes que executam ações: repetir a resposta não repete a ação certa.

Por que aprender

Os dois caches atacam o custo por lados diferentes: o de prompt barateia o contexto longo que se repete em toda chamada; o semântico elimina chamadas inteiras. Saber qual usar — e como ordenar o prompt para que o de prompt funcione — costuma render economia sem trocar de modelo.

Conceitos-chave

Cache de prompt
prefixo fixo reaproveitado
Embedding
significado em vetor
Limiar
quão parecido basta
TTL
quanto tempo a resposta vale

🌎 Multi-região e resiliência

Provedores de modelo caem, ficam lentos e aplicam limites de taxa em horários de pico — isso faz parte da operação, não é exceção. Quando a IA está no caminho crítico (atendimento, checkout, triagem), a arquitetura precisa de um plano para isso. As peças são conhecidas da engenharia de sistemas: health check (teste periódico de que um destino responde), circuit breaker (depois de falhas seguidas, o sistema para de insistir num destino por um tempo e usa a alternativa) e degradação graciosa (oferecer uma versão reduzida do recurso em vez de erro).

Em IA há um complicador: onde os dados podem ser processados. Mandar o prompt para uma região de outro país durante um failover pode ser uma transferência internacional de dados pessoais, que a LGPD regula. Por isso, a rota alternativa precisa ser aprovada antes do incidente, pelo jurídico e pela segurança — não decidida às pressas às três da manhã. Dois números orientam o desenho: RTO, quanto tempo o serviço pode ficar fora, e RPO, quanto dado (conversas, memória, índices) se aceita perder.

O que é

Resiliência multi-região é manter o serviço de IA funcionando quando um provedor, modelo ou região falha: destinos alternativos aprovados, checagem de saúde, circuit breaker, réplica dos dados de contexto e um modo degradado previsto.

Nível 1 · Retry com espera crescente. Resolve erros transitórios e limites de taxa curtos. Sempre com teto de tentativas.

Nível 2 · Fallback de modelo. Outro modelo do mesmo provedor ou um modelo local para tarefas simples.

Nível 3 · Fallback de provedor ou região. Exige contrato, avaliação de qualidade do modelo alternativo e aprovação de residência de dados.

Nível 4 · Modo degradado. Respostas prontas, fila para processar depois, ou encaminhamento para atendimento humano — com aviso honesto ao usuário.

Por que aprender

Quanto mais a IA entra em processos críticos, mais uma queda de provedor vira queda do negócio. Um plano de resiliência escrito antes do incidente — com rotas aprovadas, RTO e RPO definidos e modo degradado testado — é o que separa uma hora de lentidão de um dia de operação parada.

Conceitos-chave

Circuit breaker
para de insistir no que falha
RTO / RPO
tempo fora / dado perdido
Residência de dados
onde o dado pode ir
Modo degradado
menos recurso, sem apagão

💰 Limites de custo em escala

Em IA o custo é variável por chamada e quem decide o tamanho da chamada é, em parte, o usuário: um documento enorme colado, uma conversa que nunca termina, um agente que entra em laço chamando ferramentas. Sem limites, um único cliente ou um bug consome o orçamento do mês num fim de semana. FinOps de IA é a prática de medir, atribuir e controlar esse gasto com a mesma disciplina que se aplica à nuvem.

Os limites funcionam em camadas, todas no gateway: limite de taxa (chamadas ou tokens por minuto, por chave), teto por chamada (máximo de tokens de entrada e de saída), orçamento por tenant (valor por mês, com alertas antes de acabar) e limite de passos para agentes. Tenant é cada cliente, área ou produto que usa a plataforma e precisa ter seu gasto separado. Ao bater no limite, a melhor resposta raramente é o erro seco: é degradar para um modelo mais barato e avisar.

O que é

Limites de custo são regras aplicadas antes de cada chamada — taxa, tamanho, orçamento por tenant e passos de agente — com registro do custo real depois dela, para que o gasto seja previsível, atribuível e cortado automaticamente quando passa do combinado.

Objetivo: um guarda de orçamento por tenant, com limite por minuto e degradação para o modelo barato.

"""guarda_orcamento.py — limites por tenant antes de cada chamada. Rode: python3 guarda_orcamento.py"""
import time
from collections import defaultdict

# R$ por 1 milhão de tokens. VALORES DE EXEMPLO: troque pelos do seu contrato.
PRECOS = {"rapido": {"entrada": 0.0, "saida": 0.0},    # local: o custo é a máquina, não o token
          "forte":  {"entrada": 15.0, "saida": 60.0}}
ORCAMENTO_MES = {"cliente-a": 50.0, "cliente-b": 0.12}   # R$ por mês
LIMITE_MINUTO = {"cliente-a": 60, "cliente-b": 3}        # chamadas por minuto

gasto = defaultdict(float)
janela = defaultdict(list)

class Bloqueado(Exception):
    pass

def custo(modelo, tok_in, tok_out):
    p = PRECOS[modelo]
    return (tok_in * p["entrada"] + tok_out * p["saida"]) / 1_000_000

def autorizar(tenant, modelo, tok_in, tok_out_max):
    agora = time.time()
    janela[tenant] = [t for t in janela[tenant] if agora - t < 60]
    if len(janela[tenant]) >= LIMITE_MINUTO[tenant]:
        raise Bloqueado(f"{tenant}: limite por minuto (responda HTTP 429)")
    escolhido = modelo
    if gasto[tenant] + custo(modelo, tok_in, tok_out_max) > ORCAMENTO_MES[tenant]:
        if modelo == "rapido":
            raise Bloqueado(f"{tenant}: orçamento do mês esgotado")
        escolhido = "rapido"            # degrada em vez de negar
    janela[tenant].append(agora)
    return escolhido

def registrar(tenant, modelo, tok_in, tok_out):
    gasto[tenant] += custo(modelo, tok_in, tok_out)   # use o uso REAL devolvido pela API

if __name__ == "__main__":
    for i in range(1, 6):
        for tenant in ("cliente-a", "cliente-b"):
            try:
                m = autorizar(tenant, "forte", tok_in=2000, tok_out_max=800)
                registrar(tenant, m, 2000, 500)
                print(f"{tenant} chamada {i}: via {m:6} | gasto R$ {gasto[tenant]:.4f}")
            except Bloqueado as e:
                print(f"{tenant} chamada {i}: BLOQUEADO — {e}")

Como verificar: o cliente-a deve fazer as 5 chamadas via "forte". O cliente-b deve fazer a 1ª via "forte", a 2ª e a 3ª via "rapido" (orçamento quase no fim) e ser BLOQUEADO na 4ª e 5ª (limite de 3 por minuto). Se a saída for essa, as três camadas — orçamento, degradação e taxa — estão funcionando. Em produção, guarde gasto e janela no Redis ou no banco, não na memória do processo.

✓ Limites que funcionam

  • ✓Aplicados no gateway, iguais para todos os aplicativos.
  • ✓Alertas em degraus (por exemplo, metade, três quartos e o total do orçamento).
  • ✓Teto de passos e de tokens para cada execução de agente.
  • ✓Custo por recurso do produto, não só por fatura do provedor.

✗ Limites que falham

  • ✗Só o alerta de faturamento do provedor, que chega depois do gasto.
  • ✗Chave de API única compartilhada por todas as equipes.
  • ✗Erro seco ao estourar, sem degradação nem aviso.
  • ✗Custo estimado pelo prompt, sem conferir o uso real devolvido.

Por que aprender

Gestores aprovam IA em escala quando o custo é previsível. Com orçamento por tenant, degradação automática e custo atribuído a cada recurso do produto, a conversa sai de "a fatura veio alta" e vai para "este recurso custa tanto por usuário e vale a pena" — que é a base de qualquer decisão de investimento.

🧭 Revisão de arquitetura na prática

Tudo o que você viu se junta numa revisão de arquitetura: antes de um sistema de IA ir para produção, ou quando ele começa a crescer, alguém percorre as camadas com perguntas objetivas. A ordem importa — medir vem antes de otimizar, e limite de custo vem antes de abrir para todos os clientes.

Um assistente de IA ajuda a fazer a revisão mais completa, desde que você entregue o contexto real e proíba números inventados. Ele não substitui a medição; serve para levantar perguntas que a equipe não fez, organizar riscos e propor uma ordem de trabalho que você vai validar.

O que é

Um roteiro de revisão em sete passos, das métricas aos limites de custo, mais um prompt de análise que transforma a descrição do seu sistema numa lista priorizada de decisões, cada uma com forma de medir.

1 · Métricas. Existe painel com p95, TTFT, taxa de erro, tokens e custo por tenant e por recurso?

2 · Gateway. Algum aplicativo chama modelo direto, com chave própria? Se sim, esse é o primeiro trabalho.

3 · Roteamento. Que parte do tráfego é simples? Há conjunto de avaliação para provar que o modelo pequeno dá conta?

4 · Cache. O prefixo fixo vem antes do variável? Há perguntas repetidas que justificam cache semântico separado por tenant?

5 · Inferência. O volume é estável o bastante para comparar API com servidor próprio pelo custo por milhão de tokens?

6 · Resiliência. RTO e RPO definidos? Rota alternativa aprovada para os dados que trafegam? Modo degradado testado?

7 · Custo. Orçamento por tenant, teto por chamada, limite de passos de agente e alerta antes do fim do mês?

Objetivo: revisar a arquitetura do seu sistema de IA com um assistente (Claude, ChatGPT, Gemini).

Você é um arquiteto sênior de sistemas de IA fazendo a revisão de um desenho antes de escalar.

escreva a fórmula com variáveis e diga como eu meço o valor.

2. Avalie cada camada: métricas, gateway, roteamento, cache, inferência, resiliência, custo.
   Para cada uma: situação atual, risco principal, recomendação.
3. Liste os 3 maiores riscos (técnico, financeiro, legal), do mais grave ao menos grave.
4. Entregue uma tabela com 5 decisões priorizadas:
   Decisão | Camada | Esforço (baixo/médio/alto) | Impacto | Como medir antes e depois
5. Diga o que você NÃO consegue avaliar só com estas informações.

Como verificar: a resposta deve começar com perguntas, não com recomendações; cada decisão da tabela precisa ter uma métrica concreta (p95, custo por tenant, taxa de acerto do cache). Procure números sem fórmula — se aparecer algum, peça a origem ou a troca por variável. Leve a tabela para a equipe e valide cada linha com dados reais antes de executar.

Por que aprender

Líderes técnicos raramente desenham o sistema sozinhos; eles conduzem revisões. Um roteiro fixo garante que nenhuma camada fique esquecida, e o prompt de análise acelera a primeira versão sem trocar a medição real pela opinião do modelo.
