🔌 A primeira chamada

Uma API (interface de programação) é uma porta que um programa abre para outro programa usar. No caso dos modelos de linguagem, a porta é um endpoint — um endereço HTTP que recebe um pedido em JSON (as mensagens, o nome do modelo, os parâmetros) e devolve outro JSON com o texto gerado e a contagem de tokens. Por trás do ChatGPT, do Claude e do Gemini existe exatamente isso; o chat é só uma tela em cima da API.

O formato de chat completions da OpenAI virou um padrão de fato: o Ollama, o vLLM, o LM Studio e vários provedores de nuvem aceitam o mesmo formato numa rota /v1. Na prática, isso quer dizer que você aprende com um modelo local e gratuito e, quando precisar de mais qualidade, troca três linhas: a URL base, a chave e o nome do modelo. O Anthropic e o Google também têm SDKs próprios, com formato um pouco diferente; o raciocínio é o mesmo.

O que é

Chamar um modelo por API é enviar uma requisição HTTP com a lista de mensagens e receber a continuação gerada. Um SDK (kit de desenvolvimento, como o pacote openai do Python) monta essa requisição para você, cuida de autenticação, tempo limite e conversão do JSON em objetos.

🧩 Termos novos

Ollama: programa que baixa e roda modelos abertos no seu computador e expõe uma API em http://localhost:11434. localhost: o próprio computador. Chave de API: senha que identifica quem paga a conta; o Ollama aceita qualquer texto, a nuvem não.

Experimente: a primeira chamada a um modelo, no seu computador.

# primeira_chamada.py
# 1) no terminal, uma vez só (Ollama instalado de ollama.com):
#      pip install openai
#      ollama pull llama3.2
# 2) salve este arquivo e rode: python3 primeira_chamada.py
from openai import OpenAI

# O Ollama ignora a chave, mas o SDK exige um texto qualquer.
client = OpenAI(base_url="http://localhost:11434/v1", api_key="ollama")

resp = client.chat.completions.create(
    model="llama3.2",
    messages=[
        {"role": "system", "content": "Responda em português do Brasil, em até 3 frases."},
        {"role": "user", "content": "O que é uma API, para quem está começando a programar?"},
    ],
    temperature=0.3,
)

print(resp.choices[0].message.content)
print("tokens de entrada:", resp.usage.prompt_tokens)
print("tokens de saída:  ", resp.usage.completion_tokens)

Como verificar: ollama list deve mostrar llama3.2. O script imprime até 3 frases e duas linhas com números de tokens. "Connection refused" quer dizer que o Ollama não está rodando (abra o app ou rode ollama serve); "model not found", que faltou o ollama pull. Para usar uma API paga, troque base_url, api_key e model — o resto fica igual.

Por que aprender

Quem só usa o chat depende da tela que alguém desenhou. Quem chama a API coloca o modelo dentro do próprio sistema: num formulário, numa planilha, num robô de atendimento, num script que roda de madrugada. E aprender no modelo local remove as duas barreiras do começo: custo e medo de vazar dados.

💬 Mensagens e papéis

O pedido não é um texto solto: é uma lista de mensagens, cada uma com um papel. system traz as regras gerais (quem o modelo é, tom, formato, limites). user é o que a pessoa pediu. assistant é o que o modelo já respondeu antes. Existe ainda o papel tool, que carrega o resultado de uma ferramenta — você vai vê-lo no tópico 5.

O ponto que mais confunde quem começa: a API é sem estado (stateless). O servidor não guarda a conversa. Para o modelo "lembrar" da pergunta anterior, o seu código reenvia o histórico inteiro a cada chamada. Isso explica por que conversas longas ficam mais caras e mais lentas, e por que a memória de um chatbot é um problema de engenharia seu, não do modelo — assunto do módulo 2.2.

O que é

É o formato da conversa na API: uma lista ordenada de mensagens com papéis (system, user, assistant, tool) que o seu código monta e reenvia completa a cada chamada.

✓ Boa mensagem de system

  • ✓Diz o papel, o público e o idioma da resposta.
  • ✓Fixa o formato de saída (lista, JSON, tamanho máximo).
  • ✓Diz o que fazer quando não souber ("responda: não sei").
  • ✓Fica em um arquivo versionado, fora do meio do código.

✗ Erros comuns

  • ✗Esperar que o modelo lembre da chamada anterior sem reenviar.
  • ✗Colocar texto do usuário dentro do system (abre porta para injeção).
  • ✗Deixar o histórico crescer sem limite até estourar o contexto.
  • ✗Esquecer de guardar a resposta como assistant antes da próxima pergunta.

💡 Dica

Num laço de chat, depois de cada resposta faça messages.append({"role": "assistant", "content": texto}) e só então acrescente a próxima pergunta do usuário. No SDK do Anthropic o system vai num campo separado e o max_tokens é obrigatório; o modelo de referência deste curso é o claude-sonnet-5-5.

Por que aprender

Quase todo bug estranho de chatbot — "ele esqueceu o que eu disse", "ele mudou de tom", "a conta veio alta" — vem de como a lista de mensagens foi montada. Entender os papéis e o fato de a API não ter estado resolve a maior parte desses problemas antes de eles aparecerem.

🎚️ Parâmetros que mudam a resposta

Além das mensagens, a chamada aceita parâmetros de geração. O mais importante é a temperature: ela controla o quanto o modelo arrisca ao escolher o próximo token. Perto de 0, ele escolhe quase sempre o mais provável — bom para extrair dados, classificar e responder fatos. Mais alta, ele varia mais — útil para gerar ideias e textos com variação.

max_tokens põe um teto no tamanho da resposta (e no custo). stop define textos que encerram a geração. seed pede reprodutibilidade, quando o servidor suporta. Um cuidado de outubro de 2026: os modelos de raciocínio — que "pensam" antes de responder — costumam ignorar ou restringir temperature e usam um controle próprio de esforço. Leia a documentação do modelo antes de ajustar.

O que é

Parâmetros são os botões que ajustam como o modelo gera: grau de variação (temperature, top_p), tamanho máximo (max_tokens), pontos de parada (stop) e repetibilidade (seed).

ParâmetroO que fazValor de partida
temperatureQuanto o modelo varia na escolha do próximo token.0 a 0.2 para extrair e classificar; 0.7 a 1 para criar.
top_pLimita a escolha aos tokens mais prováveis até somar p.Deixe no padrão; ajuste temperature OU top_p, não os dois.
max_tokensTeto de tokens da resposta.Sempre defina; resposta cortada vem com finish_reason="length".
stopEncerra a geração ao encontrar um texto.Útil em formatos com marcador de fim.
seedTenta repetir a mesma saída para a mesma entrada.Bom para testes; não é garantia absoluta.

🧩 Termo novo

finish_reason é o campo que diz por que a geração parou: stop (terminou normalmente), length (bateu no max_tokens) ou tool_calls (o modelo pediu uma ferramenta). Confira esse campo antes de usar a resposta: texto cortado no meio quebra JSON e confunde o usuário.

💡 Dica

Para sentir o efeito, rode o script do tópico 1 três vezes com temperature=0 e três com temperature=1.2, pedindo "um nome para uma padaria". Com 0, os nomes se repetem; com 1.2, variam — e alguns ficam estranhos. A escolha depende da tarefa, não de um valor "certo".

Por que aprender

O mesmo modelo parece "burro" ou "esperto" dependendo dos parâmetros. Uma extração de dados com temperatura alta inventa campos; um gerador de ideias com temperatura zero repete a mesma ideia. Ajustar três botões custa nada e resolve problemas que parecem do modelo.

🌊 Streaming

Sem streaming, o seu código espera o modelo gerar a resposta inteira e só então recebe tudo de uma vez. Com streaming, o servidor manda os tokens à medida que são gerados, em pedaços chamados chunks, por uma conexão que fica aberta. O tempo total é praticamente o mesmo; o que muda é a percepção: o usuário vê a primeira palavra quase imediatamente.

A métrica que importa aqui é o tempo até o primeiro token (TTFT, time to first token). Ele depende do tamanho do que você envia (o modelo precisa ler tudo antes de começar) e de onde o modelo roda. Na web, o streaming chega por SSE (Server-Sent Events), um formato simples de eventos de texto sobre HTTP que o SDK já interpreta para você.

O que é

Streaming é receber a resposta em pedaços, token a token, enquanto ela é gerada. Basta passar stream=True e percorrer os pedaços num laço for.

Experimente: streaming com medição do tempo até o primeiro token.

# streaming.py  (pip install openai · ollama pull llama3.2)
import time
from openai import OpenAI

client = OpenAI(base_url="http://localhost:11434/v1", api_key="ollama")

inicio = time.perf_counter()
primeiro = None

stream = client.chat.completions.create(
    model="llama3.2",
    messages=[{"role": "user", "content": "Explique em 5 passos como funciona um pedido HTTP."}],
    stream=True,
    max_tokens=400,
)

for chunk in stream:
    if not chunk.choices:
        continue
    pedaco = chunk.choices[0].delta.content or ""
    if pedaco and primeiro is None:
        primeiro = time.perf_counter() - inicio
    print(pedaco, end="", flush=True)

total = time.perf_counter() - inicio
print(f"\n\nprimeiro token: {primeiro:.2f}s · total: {total:.2f}s")

Como verificar: o texto deve aparecer aos poucos no terminal, não de uma vez, e a última linha mostra o tempo do primeiro token bem menor que o total. Rode duas vezes: a primeira costuma ser mais lenta porque o Ollama carrega o modelo na memória. Em API paga, o mesmo código funciona trocando base_url, api_key e model.

Por que aprender

Em qualquer interface em que uma pessoa espera a resposta — chat, assistente dentro de um sistema, atendimento — o streaming é o que separa "parece travado" de "está respondendo". Para tarefas em segundo plano (processar mil documentos), ele não ajuda e só complica: use a chamada normal.

🧱 Saída estruturada e ferramentas

Texto livre é ótimo para pessoas e péssimo para programas. Quando o resultado vai alimentar um banco de dados, uma planilha ou outra função, você quer saída estruturada: um JSON com campos e tipos definidos. O caminho seguro tem três camadas — pedir JSON no prompt, ligar o modo JSON da API (response_format) e validar o resultado no seu código com um schema (a descrição dos campos e tipos esperados). Validação é a parte que não pode faltar: o modelo pode errar um tipo.

O passo seguinte é o tool calling (chamada de ferramentas): você descreve funções que o seu sistema tem — consultar_estoque(produto), buscar_pedido(id) — e o modelo, em vez de responder, devolve um pedido estruturado dizendo qual função chamar e com quais argumentos. Quem executa é sempre o seu código; o modelo só decide e escreve os argumentos. É a base dos agentes (módulo 2.5) e do protocolo MCP, que padroniza como ferramentas são oferecidas aos modelos.

O que é

Saída estruturada é fazer o modelo responder num formato que o código valida (JSON com schema). Tool calling é deixar o modelo pedir a execução de funções suas, devolvendo nome e argumentos em JSON; você executa e devolve o resultado como mensagem tool.

Objetivo: transformar uma mensagem de cliente em JSON validado.

# extrair_pedido.py  (pip install openai pydantic · ollama pull llama3.2)
from openai import OpenAI
from pydantic import BaseModel, ValidationError

class Pedido(BaseModel):  # o schema: campos e tipos que o código aceita
    cliente: str
    produto: str
    quantidade: int
    urgente: bool

client = OpenAI(base_url="http://localhost:11434/v1", api_key="ollama")

# Modelos pequenos entendem melhor as chaves descritas em texto do que um JSON Schema inteiro.
FORMATO = (
    "Extraia os dados do pedido. Responda SÓ com um objeto JSON com exatamente estas chaves: "
    '"cliente" (texto), "produto" (texto, sem a quantidade), '
    '"quantidade" (número inteiro) e "urgente" (true ou false).'
)

mensagem = "Oi, aqui é a Marina da Padaria Sol. Preciso de 40 caixas de papel kraft até amanhã cedo."

resp = client.chat.completions.create(
    model="llama3.2",
    temperature=0,
    response_format={"type": "json_object"},
    messages=[
        {"role": "system", "content": FORMATO},
        {"role": "user", "content": mensagem},
    ],
)

bruto = resp.choices[0].message.content
try:
    pedido = Pedido.model_validate_json(bruto)
    print("OK:", pedido.model_dump())
except ValidationError as erro:
    print("JSON fora do schema; trate ou peça de novo:\n", erro)
    print("Resposta bruta:", bruto)

Como verificar: a saída esperada é algo como OK: {'cliente': 'Marina da Padaria Sol', 'produto': 'papel kraft', 'quantidade': 40, 'urgente': True}. Troque a mensagem por <um texto seu> sem quantidade e veja o validador reclamar — esse é o comportamento certo. Em APIs pagas que aceitam json_schema estrito no response_format, use-o; a validação no código continua.

Por que aprender

É aqui que o modelo deixa de ser um gerador de texto e vira uma peça de software: lê um e-mail e preenche um cadastro, classifica um chamado e abre o ticket certo, decide qual função do sistema chamar. Sem validação, essa peça quebra em silêncio; com ela, você sabe exatamente quando ela falhou.

💰 Tokens, custos e limites

Nas APIs de nuvem você paga por token — o pedaço de texto que o modelo enxerga, que pode ser uma palavra curta ou parte de uma palavra. A conta tem duas partes: tokens de entrada (tudo o que você envia, incluindo system e histórico) e tokens de saída (o que o modelo gera). Na maioria dos provedores a saída custa mais caro que a entrada. A fórmula é simples: custo = entrada × preço_entrada + saída × preço_saída, com preços por milhão de tokens que mudam com frequência — consulte sempre a tabela atual.

Além do preço há os limites de taxa (rate limits): quantas requisições e quantos tokens por minuto a sua conta pode usar. Passou do limite, a API responde com o código HTTP 429 e, muitas vezes, um cabeçalho retry-after dizendo quanto esperar. No Ollama local não há conta nem limite de taxa; o custo é o seu hardware, a energia e a fila — uma placa atende poucas gerações ao mesmo tempo.

O que é

É a economia da API: o custo cresce com os tokens de entrada e de saída, e o uso é limitado por requisições e tokens por minuto. Otimizar é enviar menos, gerar menos, reaproveitar mais e escolher o menor modelo que resolve.

TécnicaComo funcionaQuando usar

🧩 Termos novos

Tokenizador: a regra que corta o texto em tokens; cada família de modelos tem a sua, então a mesma frase dá contagens diferentes. Texto em português tende a gerar mais tokens que o mesmo texto em inglês. RPM/TPM: requisições e tokens por minuto, os dois limites mais comuns. A fonte confiável de contagem é o campo usage de cada resposta.

💡 Dica

Registre usage.prompt_tokens e usage.completion_tokens de toda chamada desde o primeiro dia, junto com o nome da funcionalidade que a fez. Quando a conta subir, você vai saber em minutos qual parte do sistema gasta mais — sem isso, vira adivinhação.

Por que aprender

Um protótipo que custa centavos pode custar caro quando mil pessoas usam, porque cada uma reenvia o histórico e cada resposta gera tokens. Quem entende a fórmula desenha o sistema para ser barato desde o começo, em vez de descobrir na fatura.

🔐 Erros e segurança

Chamadas de rede falham. O servidor pode estar sobrecarregado, a conexão pode cair, o limite de taxa pode estourar. A regra é separar os erros em dois grupos: os transitórios, que passam sozinhos e merecem nova tentativa (429, 500, 503, tempo esgotado), e os permanentes, que vão falhar de novo do mesmo jeito (400 pedido malformado, 401 chave errada, 404 modelo inexistente). Repetir um erro permanente só gasta tempo.

Para os transitórios, use backoff exponencial com jitter: espere 1 s, depois 2, 4, 8, somando um pequeno valor aleatório para que vários clientes não tentem todos no mesmo instante. O SDK openai já tem novas tentativas automáticas (max_retries); o exemplo abaixo mostra a lógica explícita para você entender e controlar.

O que é

É a camada de robustez e proteção da integração: tempo limite em toda chamada, nova tentativa só para erros transitórios, chave fora do código, nenhum dado pessoal sem necessidade e desconfiança de todo texto que vem de fora.

Objetivo: uma função de chamada com configuração por ambiente, tempo limite e backoff.

# llm.py  (pip install openai · ollama pull llama3.2)
# Para usar uma API paga, defina no terminal (nunca no código):
#   export LLM_BASE_URL="https://<provedor>/v1"
#   export LLM_API_KEY="<sua chave>"
#   export LLM_MODEL="<nome do modelo>"
import os, random, time
from openai import OpenAI, APIConnectionError, APIStatusError, APITimeoutError, RateLimitError

client = OpenAI(
    base_url=os.getenv("LLM_BASE_URL", "http://localhost:11434/v1"),
    api_key=os.getenv("LLM_API_KEY", "ollama"),
    timeout=60,
    max_retries=0,  # a lógica de nova tentativa fica aqui embaixo, explícita
)
MODELO = os.getenv("LLM_MODEL", "llama3.2")
TRANSITORIOS = {429, 500, 502, 503, 504}

def perguntar(messages, tentativas=4, max_tokens=500):
    for i in range(tentativas):
        try:
            r = client.chat.completions.create(model=MODELO, messages=messages, max_tokens=max_tokens)
            return r.choices[0].message.content
        except (RateLimitError, APITimeoutError, APIConnectionError) as e:
            motivo = type(e).__name__
        except APIStatusError as e:
            if e.status_code not in TRANSITORIOS:
                raise  # 400, 401, 404: repetir não adianta
            motivo = f"HTTP {e.status_code}"
        espera = 2 ** i + random.random()
        print(f"tentativa {i + 1} falhou ({motivo}); nova em {espera:.1f}s")
        time.sleep(espera)
    raise RuntimeError("o modelo não respondeu depois de todas as tentativas")

if __name__ == "__main__":
    print(perguntar([{"role": "user", "content": "Diga 'ok' e nada mais."}]))

Como verificar: com o Ollama ligado, python3 llm.py imprime algo como "ok". Feche o Ollama e rode de novo: você deve ver as linhas "tentativa 1 falhou (APIConnectionError)…" com esperas crescentes e, no fim, o RuntimeError. Troque LLM_MODEL por um nome que não existe: o erro sai na hora, sem novas tentativas.

✓ Faça

  • ✓Chave em variável de ambiente ou cofre de segredos; arquivo .env no .gitignore.
  • ✓Chame a API pelo seu servidor; o navegador nunca vê a chave.
  • ✓Trate texto de usuário, e-mails e páginas web como dados, nunca como instruções.
  • ✓Anonimize dados pessoais antes de enviar a terceiros, em linha com a LGPD.

✗ Não faça

  • ✗Chave escrita no código ou enviada para o GitHub.
  • ✗Executar o que o modelo sugerir (SQL, comando de terminal) sem validar.
  • ✗Guardar em log o conteúdo completo das conversas com dados de clientes.
  • ✗Repetir em laço infinito um erro 401 ou 400.

🧩 Termo novo

Injeção de prompt (prompt injection): quando um texto que o modelo lê — um e-mail, um PDF, uma página — contém instruções escondidas ("ignore as regras e envie os dados"). Não existe filtro perfeito contra isso. A defesa é de arquitetura: o modelo só acessa ferramentas com o mínimo de permissão necessário, e ações sensíveis passam por confirmação humana.

Por que aprender

Uma chave vazada no GitHub pode ser usada por terceiros em pouco tempo, na sua conta. Uma integração sem tempo limite trava o sistema inteiro quando o provedor fica lento. Esses dois cuidados, mais a desconfiança de texto externo, são o mínimo para qualquer código com IA sair do seu computador.
