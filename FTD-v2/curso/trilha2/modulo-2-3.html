📚 O que é RAG

Um modelo de linguagem só sabe o que viu no treino. Ele não conhece o manual do seu produto, a política de trocas da sua loja nem o contrato assinado ontem. RAG (Retrieval-Augmented Generation, geração aumentada por recuperação) resolve isso em dois tempos: primeiro um sistema de busca encontra os trechos dos seus documentos que tratam da pergunta; depois o modelo recebe esses trechos junto com a pergunta e responde com base neles, citando a fonte.

A ideia foi formalizada num artigo de pesquisa de 2020 e virou o padrão para "conversar com documentos". Uma knowledge base (base de conhecimento) é o conjunto de documentos preparado para essa busca. Mesmo com modelos que aceitam janelas de contexto enormes, RAG continua útil: é mais barato enviar quatro trechos do que mil páginas, a atualização é imediata (basta reindexar um arquivo) e a citação permite conferir.

O que é

RAG é um padrão de arquitetura com duas fases: a indexação (cortar documentos em trechos, calcular embeddings, guardar num índice) e a consulta (buscar os trechos mais relevantes para a pergunta e pedir ao modelo uma resposta baseada só neles, com citação).

✓ RAG resolve bem

  • ✓Perguntas sobre documentos internos e privados.
  • ✓Conteúdo que muda (preços, políticas, estoque de artigos).
  • ✓Respostas que precisam citar fonte para auditoria.
  • ✓Controle de acesso: cada usuário só busca o que pode ver.

✗ RAG não resolve

  • ✗Ensinar um estilo ou formato fixo (isso é prompt ou fine-tuning, módulo 2.4).
  • ✗Perguntas que pedem ler tudo ("quantos contratos vencem em março?") — isso é consulta a dados estruturados.
  • ✗Documentos ruins: contraditórios ou desatualizados geram respostas iguais.
  • ✗Ausência total de alucinação: reduz, mas não elimina.

Por que aprender

É o caso de uso de IA mais pedido em empresas: assistente de suporte que lê a base de conhecimento, busca em normas internas, perguntas sobre contratos. Entender as duas fases permite diagnosticar o problema certo quando a resposta falha — e a maioria das falhas está na busca, não no modelo.

🧬 Embeddings

Um embedding é uma lista de números (um vetor) que representa o sentido de um texto. Um modelo de embedding, como o nomic-embed-text no Ollama, lê "como faço para devolver um produto?" e devolve centenas de números. O ponto é que textos com sentido parecido ganham vetores parecidos — mesmo sem palavras em comum. "Devolver" e "política de trocas" ficam perto; "horário de sábado" fica longe.

Para medir "perto", usa-se a similaridade de cosseno: o ângulo entre dois vetores. Vai de −1 a 1; quanto mais perto de 1, mais parecido o sentido. Se você normaliza os vetores (deixa todos com comprimento 1), o cosseno vira um simples produto escalar — uma conta muito rápida. Dois cuidados: use o mesmo modelo de embedding para documentos e perguntas, e saiba que trocar de modelo exige recalcular todo o índice.

O que é

Embedding é a representação de um texto como vetor num espaço em que distância significa diferença de sentido. É o que permite buscar "pelo significado" em vez de "pela palavra exata".

Experimente: calcular embeddings e comparar o sentido de três frases.

# similaridade.py
# 1) no terminal, uma vez:
#      pip install openai numpy
#      ollama pull nomic-embed-text
# 2) salve este arquivo e rode: python3 similaridade.py
import numpy as np
from openai import OpenAI

client = OpenAI(base_url="http://localhost:11434/v1", api_key="ollama")

frases = [
    "Como faço para devolver um produto com defeito?",
    "Política de trocas e devoluções de mercadorias",
    "Horário de funcionamento da loja aos sábados",
]

r = client.embeddings.create(model="nomic-embed-text", input=frases)
v = np.array([d.embedding for d in r.data])
v = v / np.linalg.norm(v, axis=1, keepdims=True)  # normaliza: cosseno = produto escalar

print("dimensões de cada vetor:", v.shape[1])
sim = v @ v.T
for i in range(len(frases)):
    for j in range(i + 1, len(frases)):
        print(f"{sim[i, j]:.3f}   {frases[i][:38]}  x  {frases[j][:38]}")

Como verificar: a primeira linha mostra 768 dimensões (o tamanho do nomic-embed-text). Das três comparações, a de "devolver" com "política de trocas" deve ter a maior nota; as que envolvem "horário" ficam mais baixas. Os valores exatos variam de modelo para modelo — o que importa é a ordem. Uma API paga de embeddings funciona igual trocando base_url, api_key e model.

Por que aprender

O usuário nunca escreve a pergunta com as mesmas palavras do documento. Embeddings são o que liga "meu boleto veio duas vezes" a um parágrafo sobre "cobrança em duplicidade". Sem entender essa ponte, fica impossível ajustar a busca quando ela erra.

✂️ Chunking

Chunking é cortar cada documento em trechos (chunks) antes de calcular os embeddings. O tamanho é um equilíbrio: trecho grande demais mistura vários assuntos e o vetor vira uma média sem foco; trecho pequeno demais perde o contexto ("o prazo é de 30 dias" — prazo de quê?). Não existe tamanho universal: teste com as suas perguntas reais e meça (tópico 7).

Três práticas melhoram quase qualquer chunking. Respeitar a estrutura: cortar em títulos e parágrafos, não no meio da frase. Sobreposição (overlap): repetir um pedaço do fim do trecho anterior no início do próximo, para não partir uma ideia ao meio. Metadados: guardar com cada trecho o arquivo, a seção, a data e quem pode ver — é isso que vira a citação e o filtro de acesso.

O que é

Chunking é a estratégia de corte dos documentos em trechos indexáveis: tamanho, ponto de corte, sobreposição e metadados de cada trecho.

EstratégiaComo cortaUse quando
Tamanho fixoA cada N caracteres ou tokens, com sobreposição.Texto corrido sem estrutura; ponto de partida.
Por estruturaTítulos, seções, parágrafos, linhas de tabela.Manuais, Markdown, documentação, contratos com cláusulas.
RecursivaTenta seção; se grande, parágrafo; se grande, frase.Documentos mistos; é o padrão de várias bibliotecas.
Pai e filhoBusca em trechos pequenos, envia ao modelo o trecho maior que os contém.Quando a busca precisa de precisão e a resposta, de contexto.

💡 Dica

Antes de mexer em tamanho, olhe os trechos. Imprima dez deles e leia como se fosse a busca: cada um faz sentido sozinho? Um PDF mal convertido — cabeçalho repetido em toda página, tabela virando sopa de números — estraga o RAG mais do que qualquer escolha de tamanho.

Por que aprender

A busca só encontra o que foi bem cortado. Um trecho que mistura frete e garantia não aparece nem para uma pergunta nem para a outra; uma regra partida ao meio chega ao modelo pela metade. Chunking é a etapa mais barata de ajustar e a que mais muda o resultado.

🔎 Busca vetorial e bancos vetoriais

Busca vetorial é calcular o embedding da pergunta e devolver os top-k trechos mais parecidos — os k vizinhos mais próximos. Com alguns milhares de trechos, comparar a pergunta com todos (busca exata, ou "força bruta") leva milissegundos num array do NumPy, e é o que o RAG do tópico 6 faz. Com milhões, entra a busca aproximada (ANN, approximate nearest neighbor), com índices como o HNSW, que trocam um pouco de precisão por muita velocidade.

Um banco vetorial guarda os vetores, os textos e os metadados, cria esses índices e permite filtrar antes de buscar ("só documentos do departamento jurídico", "só versões vigentes", "só o que este usuário pode ver"). Opções estabelecidas: Chroma (embutido, ótimo para começar), Qdrant (servidor dedicado, aberto), pgvector (extensão do Postgres — útil quando você já usa Postgres) e serviços gerenciados na nuvem.

O que é

Busca vetorial é encontrar os k vetores mais próximos do vetor da pergunta. O banco vetorial é o sistema que armazena vetores com metadados, indexa para buscar rápido e aplica filtros.

OpçãoPerfilEscolha quando
NumPy em memóriaBusca exata, zero infraestrutura.Aprender, protótipos, bases pequenas.
ChromaBiblioteca embutida no Python, grava em disco.Primeiro projeto real, um servidor só.
pgvectorVetores dentro do Postgres, junto dos seus dados.Você já usa Postgres e quer um banco só.
QdrantServidor vetorial dedicado, filtros ricos.Volume grande, busca híbrida, vários serviços.

🧩 Termos novos

top-k: quantos trechos a busca devolve; poucos podem deixar a resposta de fora, muitos enchem o prompt de ruído. HNSW: um índice em forma de grafo de "atalhos" entre vetores vizinhos, usado por vários bancos para buscar rápido em coleções grandes. Filtro por metadado: condição aplicada junto da busca, essencial para controle de acesso.

✓ Boas práticas

  • ✓Comece com NumPy ou Chroma; troque quando medir a necessidade.
  • ✓Filtre por permissão na busca, não depois da resposta.
  • ✓Guarde a versão do modelo de embedding junto do índice.

✗ Armadilhas

  • ✗Subir um cluster vetorial para quinhentos documentos.
  • ✗Misturar vetores de dois modelos de embedding no mesmo índice.
  • ✗Indexar documentos com dados pessoais sem base legal (LGPD).

Por que aprender

Escolher a ferramenta de busca pelo tamanho real do problema economiza semanas de infraestrutura. E o filtro por metadado é o que impede que um assistente interno mostre o contrato da diretoria para quem não deveria ver — um risco real em qualquer RAG corporativo.

🎯 Busca híbrida e reranking

A busca vetorial entende sentido, mas tropeça em termos exatos: um código de produto ("XR-2049"), um número de cláusula, um nome próprio raro. A busca por palavras clássica — o algoritmo BM25, usado por mecanismos de busca há décadas — faz o oposto: acha a palavra exata e ignora sinônimos. A busca híbrida roda as duas e junta as listas.

Para juntar, o método mais usado é a RRF (Reciprocal Rank Fusion): cada trecho ganha, em cada lista, a nota 1/(60 + posição), e as notas se somam. Quem aparece bem nas duas listas sobe. Depois vem o reranking: um modelo especializado (um cross-encoder, como os da família bge-reranker) lê a pergunta e cada candidato juntos, e reordena com mais precisão. É mais lento, por isso roda só sobre os 20 ou 30 primeiros da fusão.

O que é

Busca híbrida combina busca por palavras (BM25) e por sentido (vetorial) numa só lista, em geral com RRF. Reranking é uma segunda etapa que reordena os melhores candidatos com um modelo que lê pergunta e trecho juntos.

Passo 1. Faça funcionar só a busca vetorial e meça (tópico 7).

Passo 2. Se as perguntas com códigos, siglas ou nomes falham, acrescente BM25 (a biblioteca rank-bm25 no Python, ou o recurso nativo do Qdrant ou do Postgres) e funda com RRF.

Passo 3. Se o trecho certo está entre os 20 primeiros mas não entre os 4, acrescente um reranker sobre os 20.

Passo 4. Meça de novo. Cada etapa só fica se melhorar o número.

Por que aprender

Bases reais estão cheias de códigos, siglas e nomes que a busca por sentido não pega. Híbrida e reranking são as duas melhorias de busca com melhor relação esforço/resultado depois de um bom chunking — e saber em que ordem aplicá-las evita complicar o sistema sem ganho.

Conceitos-chave

BM25
busca por palavra exata
Híbrida

RRF

Reranker
segunda leitura, mais precisa

🧾 RAG mínimo com citação

Hora de juntar tudo num script só, sem framework: chunking por parágrafos com sobreposição, embeddings com o nomic-embed-text, índice salvo num arquivo JSON, busca exata por cosseno com NumPy e resposta do llama3.2 com citação no formato [arquivo#trecho]. São menos de cem linhas, e cada função corresponde a uma caixa do diagrama do tópico 1.

Dois detalhes fazem diferença. O nomic-embed-text foi treinado com prefixos de tarefa — search_document: para os trechos e search_query: para a pergunta — e funciona melhor com eles. E o prompt de resposta tem três regras: usar só os trechos, citar a fonte depois de cada afirmação e dizer "não encontrei" quando a resposta não estiver lá. Essa última é a que mais reduz a invenção.

O que é

Um RAG de ponta a ponta em Python: indexa uma pasta de arquivos .md/.txt, busca os quatro trechos mais próximos da pergunta e gera uma resposta que cita cada fonte, tudo local e gratuito pelo Ollama.

Objetivo: um RAG completo — chunking, embeddings, busca e resposta com citação.

# rag.py  (pip install openai numpy · ollama pull nomic-embed-text · ollama pull llama3.2)
# Uso: python3 rag.py <pasta-com-.md-ou-.txt> "<sua pergunta>"
import json, sys
from pathlib import Path
import numpy as np
from openai import OpenAI

client = OpenAI(base_url="http://localhost:11434/v1", api_key="ollama")
EMBED, CHAT = "nomic-embed-text", "llama3.2"
TAM, SOBRA, TOP_K = 800, 150, 4      # caracteres por trecho, sobreposição, trechos usados
INDICE = Path("indice.json")         # apague este arquivo para reindexar

def fatiar(texto, tam=TAM, sobra=SOBRA):
    """Junta parágrafos até ~tam caracteres; cada trecho novo repete o fim do anterior."""
    paragrafos = [p.strip() for p in texto.split("\n\n") if p.strip()]
    trechos, atual = [], ""
    for p in paragrafos:
        if atual and len(atual) + len(p) > tam:
            trechos.append(atual)
            atual = atual[-sobra:]
        atual = (atual + "\n\n" + p).strip()
    if atual:
        trechos.append(atual)
    return trechos

def embed(textos, prefixo):
    r = client.embeddings.create(model=EMBED, input=[prefixo + t for t in textos])
    v = np.array([d.embedding for d in r.data], dtype=np.float32)
    return v / np.linalg.norm(v, axis=1, keepdims=True)  # normalizado: cosseno = produto escalar

def indexar(pasta):
    trechos, fontes = [], []
    for arq in sorted(Path(pasta).rglob("*")):
        if arq.suffix.lower() in (".md", ".txt"):
            for i, t in enumerate(fatiar(arq.read_text(encoding="utf-8")), start=1):
                trechos.append(t)
                fontes.append(f"{arq.name}#{i}")
    vetores = np.vstack([embed(trechos[i:i + 32], "search_document: ") for i in range(0, len(trechos), 32)])
    INDICE.write_text(json.dumps({"modelo": EMBED, "fontes": fontes, "trechos": trechos,
                                  "vetores": vetores.tolist()}, ensure_ascii=False))
    print(f"indexados {len(trechos)} trechos de {len(set(f.split('#')[0] for f in fontes))} arquivos")

def carregar():
    dados = json.loads(INDICE.read_text())
    dados["vetores"] = np.array(dados["vetores"], dtype=np.float32)
    return dados

def buscar(pergunta, indice, k=TOP_K):
    q = embed([pergunta], "search_query: ")[0]
    notas = indice["vetores"] @ q
    melhores = np.argsort(-notas)[:k]
    return [(indice["fontes"][i], indice["trechos"][i], float(notas[i])) for i in melhores]

def responder(pergunta, achados):
    contexto = "\n\n".join(f"[{fonte}]\n{texto}" for fonte, texto, _ in achados)
    regras = ("Responda em português usando SÓ os trechos fornecidos. "
              "Termine CADA frase com a fonte entre colchetes, exatamente como aparece no trecho, ex.: [manual.md#2]. "
              "Se a resposta não estiver nos trechos, diga apenas: Não encontrei isso nos documentos.")
    r = client.chat.completions.create(model=CHAT, temperature=0, messages=[
        {"role": "system", "content": regras},
        {"role": "user", "content": f"Trechos:\n{contexto}\n\nPergunta: {pergunta}"},
    ])
    return r.choices[0].message.content

if __name__ == "__main__":
    pasta, pergunta = sys.argv[1], sys.argv[2]
    if not INDICE.exists():
        indexar(pasta)
    indice = carregar()
    achados = buscar(pergunta, indice)
    print("trechos recuperados:")
    for fonte, _, nota in achados:
        print(f"  {nota:.3f}  {fonte}")
    print("\n" + responder(pergunta, achados))

Como verificar: crie uma pasta docs/ com dois ou três arquivos .md seus (ou os de teste do bloco abaixo) e rode python3 rag.py docs "<uma pergunta cuja resposta está num deles>". A primeira execução imprime "indexados N trechos" e cria indice.json. Depois aparecem os quatro trechos com nota (o certo deve estar no topo) e a resposta com [arquivo#n]. Pergunte algo que não está nos arquivos: a resposta deve ser "Não encontrei isso nos documentos." Modelos pequenos como o llama3.2 às vezes esquecem a citação ou erram sinônimos; com qwen2.5 (troque CHAT) a obediência ao formato costuma melhorar. Mudou os arquivos? Apague indice.json. Para usar APIs pagas, troque base_url, api_key e os dois nomes de modelo.

🧪 Avaliação de RAG

"Parece que ficou melhor" não é medida. Avaliar um RAG começa por um conjunto de ouro (golden set): de 20 a 50 perguntas reais, cada uma com a fonte que deveria ser encontrada e, se possível, a resposta esperada. Com ele, toda mudança — tamanho de trecho, modelo de embedding, híbrida, reranker — vira um número antes e depois.

Meça as duas metades separadamente. Na busca: o hit@k (em quantas perguntas a fonte certa apareceu entre os k trechos) e o MRR (média de 1/posição da fonte certa: 1 se veio em primeiro, 0,5 em segundo…). Na resposta: fidelidade (tudo o que foi dito está nos trechos?) e relevância (respondeu o que foi perguntado?). Ferramentas como RAGAS automatizam as métricas de resposta usando um modelo como juiz — útil, desde que você confira uma amostra à mão.

O que é

Avaliar RAG é rodar um conjunto fixo de perguntas e medir, separadamente, se a busca trouxe a fonte certa (hit@k, MRR) e se a resposta ficou fiel às fontes e relevante para a pergunta.

Experimente: medir hit@k e MRR da busca do seu RAG.

# avaliar.py  (na mesma pasta do rag.py, depois de indexar)
from rag import TOP_K, buscar, carregar

# Conjunto de ouro: (pergunta, arquivo que deveria aparecer). Use perguntas REAIS dos usuários.
CASOS = [
    ("Comprei há três semanas e não gostei. Ainda posso devolver?", "trocas.md"),
    ("Em quanto tempo cai o estorno?", "trocas.md"),
    ("Produto quebrado já usado pode trocar?", "trocas.md"),
    ("Vocês entregam no domingo?", "entrega.md"),
    ("Quanto custa o frete para Belo Horizonte?", "entrega.md"),
    ("Como acompanho meu pedido?", "entrega.md"),
]

indice = carregar()
acertos, soma_rr = 0, 0.0
for pergunta, esperado in CASOS:
    fontes = [fonte for fonte, _, _ in buscar(pergunta, indice)]
    posicao = next((i for i, f in enumerate(fontes, start=1) if f.startswith(esperado + "#")), None)
    if posicao:
        acertos += 1
        soma_rr += 1 / posicao
    marca = f"posição {posicao}" if posicao else "NÃO ACHOU"
    print(f"{marca:12}  {pergunta}")

print(f"\nhit@{TOP_K}: {acertos}/{len(CASOS)}   MRR: {soma_rr / len(CASOS):.2f}")

Como verificar: com os documentos de teste, rode python3 avaliar.py: cada linha mostra em que posição a fonte certa apareceu e, no fim, o hit@4 e o MRR. Com só dois arquivos é fácil acertar tudo; o valor aparece com a sua base real. Mude TAM no rag.py, apague indice.json, reindexe e compare os números — isso é avaliar uma mudança.

✓ Avaliação que funciona

  • ✓Perguntas tiradas de chamados e conversas reais, anonimizadas.
  • ✓Inclui perguntas sem resposta nos documentos.
  • ✓Roda a cada mudança, como um teste automatizado.
  • ✓Mede busca e resposta separadas, para saber onde mexer.

✗ Avaliação que engana

  • ✗Perguntas escritas copiando frases do documento.
  • ✗Testar só olhando três respostas que "pareceram boas".
  • ✗Confiar 100% no modelo-juiz sem conferir uma amostra.
  • ✗Mudar três coisas de uma vez e não saber qual ajudou.

💡 Dica

Leia o diagnóstico na ordem certa: se o hit@k está baixo, o problema é busca ou chunking — não adianta trocar o modelo de resposta. Se o hit@k está alto e a resposta sai errada ou inventada, aí o problema está no prompt ou no modelo de geração.

Por que aprender

Sem avaliação, cada ajuste num RAG é um palpite, e melhorias numa pergunta escondem pioras em outras. Com um conjunto de ouro e duas métricas de busca, você decide com dados se vale trocar de modelo, de tamanho de trecho ou acrescentar um reranker — e consegue mostrar isso para quem paga a conta.
