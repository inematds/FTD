🧭 Do notebook ao serviço

MLOps é a prática de levar sistemas de aprendizado de máquina para produção e mantê-los funcionando, juntando o que o desenvolvimento de software já sabe (versionamento, testes, deploy automatizado, monitoramento) com problemas próprios de IA: o comportamento depende de dados e de modelos que mudam, e a saída não é determinística.

Com LLMs, muita gente fala em LLMOps. O centro de gravidade muda: em vez de treinar modelos, você costuma escolher um modelo pronto, escrever prompts, montar recuperação de documentos e ferramentas. Mas a disciplina é a mesma — e o erro mais comum também: tratar o protótipo que "funcionou na minha máquina" como se fosse um produto.

📘 Termos novos

Produção é o ambiente em que usuários reais dependem do sistema. Inferência é o uso do modelo para gerar uma resposta (o oposto de treino). Não determinístico quer dizer que a mesma entrada pode gerar saídas diferentes — por isso testes de IA medem taxas de acerto em vez de comparar um único resultado.

O que é

Um ciclo contínuo: versionar o que define o comportamento, avaliar antes de publicar, publicar aos poucos, observar em produção, responder a incidentes e transformar cada aprendizado numa nova versão.

✓ Sinais de que está pronto

  • ✓Alguém além do autor consegue subir o serviço seguindo um README.
  • ✓Existe um conjunto de testes e um número de linha de base.
  • ✓Há log de cada requisição com versão, latência e resultado.
  • ✓Voltar para a versão anterior leva minutos, não horas.

✗ Sinais de protótipo

  • ✗O prompt mora numa célula de notebook e muda sem registro.
  • ✗"Testar" é rodar três exemplos e achar que ficou bom.
  • ✗Ninguém sabe quanto o sistema custa por mês.
  • ✗O problema só aparece quando o cliente reclama.

Por que aprender

Fazer um protótipo com LLM ficou fácil; manter um serviço confiável continua difícil. Quem domina o ciclo completo consegue colocar IA em uso real, defender o projeto com números e dormir tranquilo depois do deploy.

🗂️ Versionar tudo

Num software comum, o código define o comportamento. Num sistema com IA, o comportamento depende de cinco coisas ao mesmo tempo: o código, o prompt, o modelo, os dados (de treino, de avaliação e da base consultada) e a configuração (temperatura, limites de tokens, ferramentas liberadas). Se qualquer uma mudar sem registro, você não consegue explicar por que a resposta de hoje é diferente da de ontem.

A regra prática: prompt é código. Fica num arquivo no repositório, passa por revisão e ganha versão. O modelo é fixado por nome e versão exata, nunca por um apelido como "latest" ou "o mais novo" — provedores e o próprio Ollama atualizam apelidos, e o comportamento muda sem você mexer em nada.

📘 Termos novos

Registro de modelos (model registry) é um catálogo de versões de modelo com métricas e estado (teste, produção, aposentado) — o MLflow tem um. DVC é uma ferramenta que versiona arquivos de dados grandes ao lado do git. Release é o pacote com nome único que junta as versões de tudo o que vai para produção.

O que é

Dar a cada versão em produção um identificador que aponta para o commit do código, a versão do prompt, o modelo exato, a versão dos dados de avaliação e a configuração usada — de forma que qualquer resposta possa ser reproduzida.

O quêOnde versionarErro comum
Códigogit, com tag por releaseDeploy de algo que não está commitado
PromptArquivo no repositório, revisado em PREditar o prompt direto no painel do provedor
ModeloNome e versão fixos na configuração; registro de modelosUsar apelido que o provedor atualiza
DadosDVC, bucket com versão ou tabela com dataConjunto de testes editado sem histórico
ConfiguraçãoArquivo de config ou variáveis de ambiente versionadasTemperatura diferente em cada ambiente

💡 Dica

No Ollama, ollama show <modelo> mostra os detalhes do modelo instalado e ollama list mostra o identificador de cada um. Registre esse identificador junto da release: se alguém rodar ollama pull de novo e o modelo mudar, você vai perceber.

Por que aprender

Sem versionamento completo, não há como investigar um incidente, comparar duas versões nem cumprir um pedido de auditoria ("qual sistema decidiu isto em março?"). É barato de fazer no começo e caríssimo de reconstruir depois.

🧪 Avaliação contínua

No módulo 2.7 você montou um conjunto de testes e mediu um classificador à mão. Aqui ele vira portão de qualidade: um teste automatizado que roda a cada mudança de prompt, modelo ou código e bloqueia a publicação se o resultado cair abaixo da linha de base. É o mesmo princípio dos testes de software, adaptado a saídas que variam.

Há três camadas de avaliação. Checagens determinísticas: o JSON é válido, o rótulo está na lista, a resposta não passa do tamanho. Métricas contra respostas certas: acurácia, precisão, revocação. E, para textos abertos, LLM como juiz com uma rubrica escrita — útil, mas precisa ser conferido contra notas humanas numa amostra.

📘 Termos novos

CI (integração contínua) é rodar testes automaticamente a cada commit, em serviços como GitHub Actions ou GitLab CI. Regressão é quando algo que funcionava para de funcionar depois de uma mudança. LLM como juiz é usar um modelo para dar nota a respostas de outro, seguindo critérios explícitos.

O que é

Rodar automaticamente o conjunto de testes a cada mudança e tratar queda de qualidade como teste falhando: a versão não segue para produção até alguém explicar ou corrigir.

Experimente: portão de qualidade com pytest, usando o classificador.py do módulo 2.7.

# Instalação: pip install pytest openai   |   ollama pull qwen2.5:7b
# Estrutura:  classificador.py   evals/casos.jsonl   test_qualidade.py
#
# evals/casos.jsonl — um caso por linha (troque por 30+ exemplos reais anonimizados):
# {"texto": "Meu pedido está parado há uma semana", "esperado": "entrega"}
# {"texto": "O boleto venceu e não consigo gerar outro", "esperado": "pagamento"}

# test_qualidade.py
import json
import pathlib
from classificador import classificar, ROTULOS

CASOS = [json.loads(l) for l in
         pathlib.Path("evals/casos.jsonl").read_text(encoding="utf-8").splitlines() if l.strip()]
LINHA_DE_BASE = 0.80   # <troque pelo valor medido na versão atual em produção>

def test_formato_valido():
    for caso in CASOS[:5]:
        saida = classificar(caso["texto"])
        assert saida["rotulo"] in ROTULOS, saida

def test_acuracia_nao_cai():
    erros = []
    for caso in CASOS:
        previsto = classificar(caso["texto"])["rotulo"]
        if previsto != caso["esperado"]:
            erros.append((caso["texto"], caso["esperado"], previsto))
    acc = 1 - len(erros) / len(CASOS)
    print(f"\nacurácia={acc:.0%} (linha de base {LINHA_DE_BASE:.0%})")
    for e in erros:
        print("  ERRO:", e)
    assert acc >= LINHA_DE_BASE, f"regressão: {acc:.0%} < {LINHA_DE_BASE:.0%}"

Como verificar: rode pytest -q -s test_qualidade.py. Com o prompt atual, os dois testes devem passar e mostrar a acurácia. Agora estrague o prompt de propósito (troque a lista de rótulos na instrução) e rode de novo: test_acuracia_nao_cai deve falhar com a mensagem "regressão". Esse é o portão funcionando.

Determinístico

Formato, campos obrigatórios, tamanho, palavras proibidas. Barato e rápido: rode sempre.

Com gabarito

Acurácia e métricas por rótulo contra respostas anotadas por pessoas. É o portão principal.

LLM como juiz

Para respostas abertas. Rubrica escrita e conferência periódica contra notas humanas.

Por que aprender

Prompts e modelos mudam o tempo todo, e uma melhoria num caso costuma piorar outro. O portão automático transforma "acho que ficou melhor" em um número comparável e impede que uma regressão silenciosa chegue aos usuários.

🚀 Deploy e serving

Serving é colocar o modelo atrás de uma interface estável — quase sempre uma API HTTP — que outros sistemas chamam. O serviço precisa de coisas que o notebook não tinha: validação da entrada, limite de tempo para cada chamada, resposta de reserva quando o modelo falha, um endpoint de saúde e um log por requisição.

Quanto à forma de rodar: tempo real (a resposta volta na hora, como num chat) ou lote (processa milhares de itens de madrugada, mais barato e tolerante a demora). O modelo pode ser uma API externa ou um servidor próprio — Ollama para começar, servidores como vLLM quando o volume cresce — empacotado em contêiner Docker para rodar igual em qualquer máquina.

📘 Termos novos

Fallback é a resposta de reserva quando a principal falha (um rótulo "outro", uma mensagem padrão, um modelo alternativo). Deploy canário é mandar uma fração pequena do tráfego para a versão nova e ampliar aos poucos se as métricas ficarem boas. Rollback é voltar para a versão anterior.

O que é

Embrulhar o modelo num serviço com contrato claro (entrada, saída, erros), limites de tempo e tamanho, resposta de reserva e publicação gradual com caminho de volta rápido.

Objetivo: um serviço de classificação com timeout, fallback, saúde e log estruturado (app.py).

# Instalação: pip install fastapi uvicorn openai   |   ollama pull qwen2.5:7b
import json, logging, time, uuid
from fastapi import FastAPI, HTTPException
from pydantic import BaseModel
from openai import OpenAI

VERSAO = "classificador-1.4.2"          # <a release que está no ar>
MODELO = "qwen2.5:7b"
ROTULOS = {"entrega", "pagamento", "produto", "elogio", "outro"}
client = OpenAI(base_url="http://localhost:11434/v1", api_key="ollama",
                timeout=20, max_retries=1)   # nunca espere para sempre
logging.basicConfig(level=logging.INFO, format="%(message)s")
log = logging.getLogger("servico")
app = FastAPI()

class Pedido(BaseModel):
    texto: str

@app.get("/health")
def health():
    return {"ok": True, "versao": VERSAO, "modelo": MODELO}

@app.post("/classificar")
def classificar(p: Pedido):
    if not p.texto.strip() or len(p.texto) > 4000:
        raise HTTPException(422, "texto vazio ou longo demais")
    rid, t0, tokens = str(uuid.uuid4()), time.perf_counter(), 0
    try:
        r = client.chat.completions.create(
            model=MODELO, temperature=0, response_format={"type": "json_object"},
            messages=[{"role": "system", "content": "Classifique em: " + ", ".join(sorted(ROTULOS))
                       + '. Responda só {"rotulo": "..."}'},
                      {"role": "user", "content": p.texto}])
        rotulo = json.loads(r.choices[0].message.content).get("rotulo")
        tokens = r.usage.total_tokens if r.usage else 0
        status = "ok" if rotulo in ROTULOS else "fora_da_lista"
    except Exception as e:                     # timeout, modelo fora do ar, JSON inválido
        rotulo, status = None, f"erro:{type(e).__name__}"
    if rotulo not in ROTULOS:
        rotulo = "outro"                       # fallback: o sistema nunca devolve lixo
    ms = round((time.perf_counter() - t0) * 1000)
    log.info(json.dumps({"rid": rid, "versao": VERSAO, "status": status,
                         "ms": ms, "tokens": tokens, "rotulo": rotulo}))
    return {"rotulo": rotulo, "status": status, "versao": VERSAO, "request_id": rid}

Como verificar: suba com uvicorn app:app --port 8000 2>&1 | tee servico.log. Em outro terminal: curl -s localhost:8000/health deve devolver a versão; curl -s -X POST localhost:8000/classificar -H 'Content-Type: application/json' -d '{"texto":"meu pedido não chegou"}' deve devolver "rotulo":"entrega". Pare o Ollama e repita: a resposta deve vir com "rotulo":"outro" e status de erro, sem derrubar o serviço.

💡 Dica

Antes do canário, existe um degrau ainda mais seguro: o modo sombra. A versão nova recebe uma cópia das requisições reais, mas a resposta dela não vai para o usuário — só para o log, onde você compara com a versão estável.

Por que aprender

Modelos ficam lentos, saem do ar e devolvem formatos inesperados. Um serviço com timeout, fallback e deploy gradual transforma essas falhas em degradação controlada, em vez de tela de erro para o cliente.

📈 Monitoramento

Um sistema com IA pode estar "no ar" e, ao mesmo tempo, errado. O servidor responde em tempo, sem erro HTTP, mas a qualidade caiu porque os clientes começaram a escrever sobre um assunto novo ou porque o provedor trocou o modelo. Por isso o monitoramento olha quatro famílias de sinais: técnicos, de qualidade, de custo e de dados.

A base é o log estruturado que o serviço do tópico 4 já grava: uma linha JSON por requisição, com versão, status, latência e tokens. A partir dela você monta painéis (Grafana), alertas e rastreamento entre serviços (OpenTelemetry). Para LLMs há ferramentas específicas de observabilidade, como o Langfuse, de código aberto, que guardam prompt, resposta e avaliação de cada chamada.

📘 Termos novos

Percentil: o p95 de latência é o tempo abaixo do qual ficam 95% das requisições — mostra a experiência dos usuários mais azarados, que a média esconde. Drift (deriva) é a mudança, ao longo do tempo, no tipo de dado que chega ou na relação entre dado e resposta certa. Observabilidade é conseguir responder "por que isso aconteceu?" a partir dos registros.

O que é

Acompanhar continuamente se o serviço está rápido, disponível, correto e dentro do orçamento, com alertas que avisam antes do usuário — e registros suficientes para investigar cada caso.

FamíliaO que medirAlerta típico
TécnicoLatência p50/p95, taxa de erro, timeoutsp95 acima do combinado por 10 minutos

Experimente: calcular p50, p95, erros e distribuição de rótulos a partir do servico.log.

# metricas.py — sem dependências externas
import json, statistics, sys
from collections import Counter

linhas = []
for l in open(sys.argv[1] if len(sys.argv) > 1 else "servico.log", encoding="utf-8"):
    l = l.strip()
    if l.startswith("{"):
        try:
            linhas.append(json.loads(l))
        except json.JSONDecodeError:
            pass

if len(linhas) < 2:
    sys.exit("poucas requisições no log; faça algumas chamadas antes")

ms = [x["ms"] for x in linhas]
q = statistics.quantiles(ms, n=100, method="inclusive")  # q[49] = p50, q[94] = p95
status = Counter(x["status"] for x in linhas)
rotulos = Counter(x["rotulo"] for x in linhas)
nao_ok = sum(v for k, v in status.items() if k != "ok")

print(f"requisições: {len(linhas)}")
print(f"latência p50={q[49]:.0f} ms  p95={q[94]:.0f} ms  máx={max(ms)} ms")
print(f"não-ok: {nao_ok / len(linhas):.1%}  {dict(status)}")
print(f"tokens/req (média): {statistics.mean(x['tokens'] for x in linhas):.0f}")
print("rótulos:", {k: f"{v / len(linhas):.0%}" for k, v in rotulos.most_common()})

Como verificar: com o serviço do tópico 4 no ar, faça umas 20 chamadas com textos variados e rode python3 metricas.py servico.log. Você deve ver p50 menor que p95, a fração de não-ok e a distribuição de rótulos. Pare o Ollama, faça mais chamadas e rode de novo: a fração de não-ok tem que subir. É esse número que um alerta vigia.

Por que aprender

Sistemas com IA degradam em silêncio. Quem mede latência, qualidade, custo e drift descobre o problema numa segunda-feira de manhã olhando um painel — e não numa sexta à noite pela reclamação de um cliente importante.

💰 Custo e desempenho

Em APIs pagas, o custo é proporcional a tokens: os de entrada (prompt, documentos, histórico) e os de saída (a resposta), em geral com preços diferentes. Em modelos locais, o custo vira hardware, energia e manutenção. Nos dois casos, as mesmas alavancas funcionam: mandar menos texto, gerar menos texto, usar o menor modelo que resolve e não repetir trabalho.

Desempenho e custo andam juntos: menos tokens também significam respostas mais rápidas. A ordem que costuma dar mais resultado é medir primeiro (quanto custa cada tipo de requisição), cortar o desperdício óbvio (histórico inteiro reenviado, documentos que não precisavam ir) e só depois partir para trocas de modelo.

📘 Termos novos

Cache de prompt: vários provedores cobram menos quando o começo do prompt se repete entre chamadas — por isso instruções fixas vão no início e o conteúdo variável no fim. Roteamento de modelos: um modelo pequeno atende os casos simples e só os difíceis vão para o grande. Quantização: guardar os pesos do modelo com menos bits para caber em menos memória, com alguma perda de qualidade.

O que é

Medir o custo e a latência por tipo de requisição e aplicar alavancas — prompt enxuto, limite de saída, cache, lote, roteamento e modelo menor — conferindo no conjunto de testes que a qualidade não caiu.

✓ Alavancas que funcionam

  • ✓Limite de tokens de saída e formato curto (JSON em vez de parágrafo).
  • ✓Instruções fixas no início do prompt, para aproveitar cache.
  • ✓Processar em lote o que não precisa de resposta imediata.
  • ✓Guardar respostas de perguntas idênticas e repetidas.

✗ Economias que custam caro

  • ✗Trocar de modelo sem rodar o conjunto de testes.
  • ✗Cortar o contexto até o modelo começar a inventar.
  • ✗Cache de respostas que dependem do usuário ou do momento.
  • ✗Tirar timeout e retentativa para "ganhar velocidade".

Objetivo: estimar o custo mensal de um fluxo em API paga a partir dos tokens medidos.

# custo.py — preencha com os SEUS números (preços mudam; confira a página do provedor)
PRECO_ENTRADA_POR_MILHAO = 0.0   # <US$ por 1 milhão de tokens de entrada>
PRECO_SAIDA_POR_MILHAO = 0.0     # <US$ por 1 milhão de tokens de saída>
COTACAO_DOLAR = 0.0              # <R$ por US$ no dia>

FLUXOS = {  # nome: (requisições por dia, tokens de entrada, tokens de saída) — médias medidas
    "triagem":  (2000, 350, 20),
    "resumo":   (150, 6000, 400),
    "<outro>": (0, 0, 0),
}

total = 0.0
for nome, (req, t_in, t_out) in FLUXOS.items():
    dia = req * (t_in * PRECO_ENTRADA_POR_MILHAO + t_out * PRECO_SAIDA_POR_MILHAO) / 1_000_000
    mes = dia * 30 * COTACAO_DOLAR
    total += mes
    print(f"{nome:10s} R$ {mes:10.2f}/mês   ({req} req/dia, {t_in}+{t_out} tokens)")
print(f"{'TOTAL':10s} R$ {total:10.2f}/mês")
# Simule: o que acontece se o resumo cortar a entrada pela metade? E com metade das requisições?

Como verificar: pegue as médias de tokens do metricas.py (tópico 5) e os preços atuais do provedor. Rode python3 custo.py e confira um fluxo à mão com a calculadora. O fluxo com maior custo mensal é onde começar a otimizar — muitas vezes não é o que tem mais requisições.

Por que aprender

Projetos de IA são cancelados por custo imprevisível com mais frequência do que por falta de qualidade. Saber estimar, medir e reduzir o gasto sem perder acerto é o que permite levar um piloto para toda a empresa.

🚨 Incidentes e rollback

Incidente em sistema com IA nem sempre é "caiu". Pode ser o assistente respondendo com um tom inadequado, um classificador mandando tudo para "outro", um agente executando uma ação que não devia ou um gasto que triplicou numa noite. A resposta segue a mesma ordem: primeiro conter o dano, depois entender a causa.

Conter costuma ser uma de três ações: voltar para a release anterior (rollback), desligar a funcionalidade por uma chave de configuração ou ativar o modo degradado (fallback para regra simples ou atendimento humano). Tudo isso precisa estar pronto e testado antes do incidente — num runbook, não na cabeça de uma pessoa.

📘 Termos novos

Runbook é o roteiro escrito do que fazer em cada tipo de problema, com comandos prontos. Feature flag é uma chave de configuração que liga ou desliga uma funcionalidade sem novo deploy. Pós-mortem sem culpa é a análise do incidente focada em causas e proteções, não em culpados — as pessoas contam o que realmente aconteceu.

O que é

Um processo combinado de antemão para detectar, conter, comunicar, corrigir e aprender com falhas, terminando sempre com uma proteção nova — em geral um caso a mais no conjunto de testes ou um alerta a mais.

1 · Detectar. Alerta do monitoramento ou relato de usuário. Registre a hora e a release no ar.

2 · Conter. Rollback, feature flag ou modo degradado. Investigar vem depois.

3 · Comunicar. Quem é afetado, o que já foi feito e quando sai a próxima atualização.

4 · Corrigir. Reproduza com a release e o log da requisição; corrija; passe pelo portão de qualidade.

5 · Aprender. Pós-mortem sem culpa e uma proteção nova: caso de teste, alerta ou limite.

Objetivo: um runbook mínimo (RUNBOOK.md) para deixar no repositório do serviço.

# RUNBOOK — <nome do serviço>
Responsável de plantão: <nome / canal>     Painel: <link do painel>
Release atual: <ex.: classificador-1.4.2>  Release anterior estável: <1.4.1>

## Sintoma A — taxa de fallback ou de erro sobe
1. Conferir /health e se o modelo responde (ollama ps / status do provedor).
2. Se começou após um deploy: ROLLBACK -> <comando ou passo exato>.
3. Se o modelo está fora: ativar modo degradado -> <flag/variável e valor>.

## Sintoma B — respostas inadequadas (tom, conteúdo, ação errada)
1. Desligar a funcionalidade: <feature flag> = off.
2. Salvar 5 exemplos (request_id) para reprodução, sem dados pessoais.
3. Avisar <área responsável> e o encarregado de dados se houver dado pessoal.

## Sintoma C — custo diário acima de <limite>
1. Ver tokens por fluxo (metricas.py) e o fluxo que mudou.
2. Reduzir limite de requisições: <config>.  3. Investigar laço ou abuso.

## Depois de todo incidente
- [ ] Pós-mortem sem culpa em até <N> dias úteis (linha do tempo, causa, proteções)
- [ ] Caso novo em evals/casos.jsonl reproduzindo o problema
- [ ] Alerta ou limite novo, se o problema foi descoberto tarde

Como verificar: faça um ensaio. Peça a alguém do time que não escreveu o serviço para executar o Sintoma A seguindo só o runbook, com o Ollama parado de propósito. Se a pessoa precisar perguntar alguma coisa, a resposta vai para o runbook.

💡 Dica

Mantenha um registro de uma linha por falha: data, o que quebrou, a menor correção possível e se a causa foi de prompt ou de infraestrutura. Depois de algumas linhas, o padrão aparece e você para de reconstruir o que só precisava de uma proteção.

Por que aprender

Todo sistema em produção vai falhar em algum momento. A diferença entre um incidente de cinco minutos e um de cinco horas é ter o caminho de volta pronto e ensaiado — e a diferença entre um time que repete erros e um que melhora é o pós-mortem que vira proteção.
